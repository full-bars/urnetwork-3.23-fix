# v3.23.0-fix.32.8

> [!NOTE]
> This release teaches the provider to protect a box that is running short of memory, and adds a measured-cost smart dialer. Both are conservative by default: the OOM-aware start cap runs in `shadow` mode (it decides and logs, and enforces nothing) and the smart dialer is off. A default provider changes only in what it logs, a small local record it now keeps of its own behaviour, and the corrections below. `urnet-tools status` now calls an upgrade an `update` instead of a crash, and a node whose limits are short for its pool says so at startup.

> [!NOTE]
> Known limitation. A plain `systemctl restart` reads `last restart: unclean`, the same as a crash. The clean-shutdown marker is consumed when it is read so that a real crash is never mislabeled clean, and a mislabeled restart is cosmetic while a missed crash is a blind spot. Telling the two apart is tracked in [#707](https://github.com/full-bars/urnetwork-3.23-fix/issues/707). An in-place upgrade reads `update`.

## What's Changed

### Added

- **An OOM-aware start cap, shadow by default** ([#700](https://github.com/full-bars/urnetwork-3.23-fix/pull/700)): when the kernel OOM-killed this provider's own cgroup subtree since the previous start (same boot, higher `oom_kill` counter; a reboot is never blamed), the next start runs 80% of the peak running proxies instead of the load that just died. The cap never goes below the larger of 50 and a quarter of the desired pool, takes at most three reductions per 24 hours and then freezes, relaxes 10% at a start that comes a full clean day after the last change, and clears at the desired size. It never writes your `proxy trim` file: the tighter of the two caps applies. In `shadow` it logs what it would do and enforces nothing.
- **A kill switch for it** ([#700](https://github.com/full-bars/urnetwork-3.23-fix/pull/700)): `urnet-tools set oom-cap on|off|shadow`, or `URNETWORK_OOM_CAP` in the unit. It is persisted, validated, live and acknowledged in the log. Any source saying `off` wins, including against `URNETWORK_OOM_CAP=on`. Switching to `on` logs what it will cost, the cap now in force and how many running proxies the next reload would drop.
- **An audit ledger of capacity decisions and `urnet-tools autopilot log [limit]`** ([#700](https://github.com/full-bars/urnetwork-3.23-fix/pull/700), [#701](https://github.com/full-bars/urnetwork-3.23-fix/pull/701)): every OOM-cap decision and every trim result is appended to `~/.urnetwork/autopilot.jsonl` (time, actor, action, from, to, mode, reason; capped at 256 KiB, newest lines kept). `autopilot log` shows it as a timeline, marks shadow decisions `[shadow]`, and prints the current `oom-cap` value. A provider that predates the `ledger` command gets an explanatory error.
- **A low memory headroom log** ([#700](https://github.com/full-bars/urnetwork-3.23-fix/pull/700)): host or cgroup available memory below the larger of 150 MiB and 10% of RAM, capped at 400 MiB, for two consecutive 30 second samples logs `[proxy][resources] low memory headroom`, and `recovered` once four samples sit 25% above the line. It changes nothing. Connected clients drive memory, so a box can get short with no change in its proxy count.
- **Startup warnings when the memory limits are short for the pool** ([#699](https://github.com/full-bars/urnetwork-3.23-fix/pull/699), [#700](https://github.com/full-bars/urnetwork-3.23-fix/pull/700), [#705](https://github.com/full-bars/urnetwork-3.23-fix/pull/705)): two independent checks, the finite `GOMEMLIMIT` against the heap the pool needs and the whole-process footprint against the RAM the box gives the provider, each with a peak allowance for connected clients. A `GOGC` pinned under `URNETWORK_PROFILE=auto`, which disables the adaptive governor, is flagged too. The provider never changes these values. A new `effective RAM ceiling` line says once at startup which limit set the ceiling.
- **Trim commands leave a receipt in the log** ([#698](https://github.com/full-bars/urnetwork-3.23-fix/pull/698)): `[proxy][trim] received: cap=N (was X); R running, D desired, applying` once per change, an `applied:` result line even when nothing needed shedding, and `received: cap cleared`.
- **`urnet-tools smart-dialer [status|on|off]`** ([#704](https://github.com/full-bars/urnetwork-3.23-fix/pull/704)): transport scoring carried a hardcoded 500 ms latency baseline that assumed what the network costs. With the smart dialer on, weights come from success ratio and error streak, then scale by measured connect cost relative to the fastest transport that works on this network, and serial attempts try measured-faster transports first. It never removes a transport, failures keep their authority (a blocked transport still loses to a slow working one), a client with one working transport is unaffected, and below a sample floor the existing order stands. Off by default, live, persisted and re-applied at startup. With it off, scoring is exactly what it was. The plan is to turn it on by default in a later release once it has had more testing, so trying it now and reporting what you see is what gets it there.
- **Background probes so the smart dialer can compare** ([#709](https://github.com/full-bars/urnetwork-3.23-fix/pull/709)): the first-choice transport wins wherever it works, so the others were never dialed and never measured. Each proxy's client strategy now probes every transport with connect-only attempts (each one is a real request to the API on its own connection, not gated by the startup auth admission gate) after a jittered startup delay and every 5 minutes, all in one round so the samples are comparable. A failed probe never demotes a transport that has real successes, probing stops as soon as the smart dialer is turned off, and it is skipped while custom extenders are configured. It does nothing while the smart dialer is off.
- **An `emoji` package** ([#708](https://github.com/full-bars/urnetwork-3.23-fix/pull/708)): network tag validation and suggestion, copied verbatim from upstream. The SDK imports it and consumers that use this repository as their connect replace target failed to build without it. No provider behavior changes.
- **A built-in baseline recorder** ([#712](https://github.com/full-bars/urnetwork-3.23-fix/pull/712)): every provider keeps a small local record of how it behaves in `~/.urnetwork/baseline.jsonl` (1 MiB, newest whole lines kept): a start mark at launch, then one sample every 15 minutes, the first at 5 minutes. On by default and with no setup, so an upgrade can be judged against what the box did before it instead of against a baseline somebody remembered to take. Counts and totals only, never proxy addresses, usernames or passwords, and a field that could not be measured is omitted rather than written as zero. `urnet-tools baseline show` prints the newest rows, `baseline mark <label>` annotates the timeline (for example just before an upgrade), and `baseline compare` reports billable rate, proxies up, memory, restarts and OOM kills across an upgrade. The rate comes from the lifetime byte counter's delta over the time delta, the ramp after each start is excluded from both sides, a segment under four samples prints `insufficient data`, and a capacity change is warned about so a trimmed box is not read as a regression. In Docker the host memory figure is the tighter of host and cgroup, with its source recorded. `urnet-tools set baseline off` stops recording at once and keeps the existing file; `URNETWORK_BASELINE_INTERVAL` changes the sample interval (floor one minute).
- **The pressure monitor, pool controller and degraded-proxy reaper are supervised**: a panic in any of them used to end that loop for good, leaving the last pressure score, a tightened GOGC and a shrunk memory budget in force, and a high last score kept the pool controller cutting toward its floor. They now restart with exponential backoff, and the pressure monitor puts its score, memory budget and GOGC back to neutral whenever it exits. `urnet_loop_restarts_total` and `urnet_loop_up` show it per loop.
- **GC state, conntrack fill and TCP socket states are recorded**: `baseline.jsonl` and `/metrics` now carry GOGC in force, whether the governor is tightening, the GC CPU share, `nf_conntrack_count` over `nf_conntrack_max`, TIME_WAIT sockets and orphaned sockets. Observation only, Linux only, and a reading the box cannot supply is left out instead of written as zero. Conntrack overflow drops packets silently, so this is the first place it shows.

### Fixed

- **The OOM kill switch never turned the feature off** ([#706](https://github.com/full-bars/urnetwork-3.23-fix/pull/706)): `set oom-cap off` was treated as a clear like every other off value, which re-applies the default, and the default is `shadow`. It now disables the feature, forgets a standing cap so it cannot rebind when the switch goes back on ([#705](https://github.com/full-bars/urnetwork-3.23-fix/pull/705)), and takes effect at once instead of at the next reload ([#702](https://github.com/full-bars/urnetwork-3.23-fix/pull/702)). The marker heartbeat also runs while the feature is off, so a box left off for a weekend does not refuse its first real OOM kill.
- **An upgraded box reported itself as a crash** ([#706](https://github.com/full-bars/urnetwork-3.23-fix/pull/706)): `last restart: unclean (v3.23.0-fix.32.1 to v3.23.0-fix.32.7)` for days after an ordinary update. The restart-reason marker expired after 10 minutes although it is written before the binary is fetched, any version change read as a crash, and the clean-shutdown marker was deleted on read. `status` now reports `update` after an upgrade, and a box that really crashed still reports `unclean`.
- **A crash could be reported as clean** ([`855339684`](https://github.com/full-bars/urnetwork-3.23-fix/commit/855339684)): the clean-shutdown marker was left on disk, and a crash never runs the clean-exit path, so after one clean shutdown every later OOM kill found the stale file and was reported clean. It is consumed on read again. See the known limitation above.
- **An unreadable `proxy_url.json` could destroy the pool state** ([#706](https://github.com/full-bars/urnetwork-3.23-fix/pull/706)): one transient read error made the merge cycle substitute an empty state and write it back, erasing every cached entry, persisted grade and the whole blacklist, and made a reload cancel every running URL proxy. An unreadable file is now skipped, not treated as empty. A missing file is still normal.
- **Retention events were dropped on a slow disk** ([#706](https://github.com/full-bars/urnetwork-3.23-fix/pull/706)): the retention writer opened, wrote and closed per event, so its 256 slot buffer stayed full exactly when a box was misbehaving. It now drains in batches of 64 with the file held open. The retention log also rotates before the write that would cross the limit, not after, so the newest events are no longer lost ([`2465f9e`](https://github.com/full-bars/urnetwork-3.23-fix/commit/2465f9e2f)), and its two writers rotate under one lock.
- **The action ledger never trimmed when the newest line was oversized** ([`bd6cdfad`](https://github.com/full-bars/urnetwork-3.23-fix/commit/bd6cdfad2)): the guard kept everything from byte 0, so every append re-ran a useless trim. Trimming also wrote a zero byte file in one case, discarding the audit trail ([#706](https://github.com/full-bars/urnetwork-3.23-fix/pull/706)).
- **Trim shed a proxy's state along with the proxy** ([#698](https://github.com/full-bars/urnetwork-3.23-fix/pull/698)): a shed proxy lost its ID, health, downtime and grade history and relaunched ungraded. It now keeps its entry, like a credential rotation does. A shed proxy that finishes draining no longer triggers a wasted reload ([#702](https://github.com/full-bars/urnetwork-3.23-fix/pull/702)).
- **The trim cap is written atomically and read honestly** ([#705](https://github.com/full-bars/urnetwork-3.23-fix/pull/705)): the old write truncated first, so a reader could see an empty file, which means no cap. A garbage value is reported once per distinct value, and an unreadable cap file no longer blocks the automatic cap.
- **The status denominator ignored the trim cap** ([#698](https://github.com/full-bars/urnetwork-3.23-fix/pull/698)): a healthy box trimmed to 2000 read `critical: 2001/4127`. The configured count is now capped at the trim target.
- **`proxy trim --preview` always answered "nothing to shed"** ([#698](https://github.com/full-bars/urnetwork-3.23-fix/pull/698)): it built its running set in the short-lived CLI process, where the health registry is empty. The running provider now computes it, and the CLI says so when it cannot reach one.
- **The trim cap is honored before launching at startup** ([#699](https://github.com/full-bars/urnetwork-3.23-fix/pull/699)): a restart used to open every desired proxy and only then shed down, a burst of thousands of connections on exactly the boxes short of memory. Held proxies stay desired and are admitted when the cap is raised.
- **The goroutine pressure sensor now judges per proxy** ([#699](https://github.com/full-bars/urnetwork-3.23-fix/pull/699), [#702](https://github.com/full-bars/urnetwork-3.23-fix/pull/702)): a healthy proxy costs 20 to 27 goroutines, so the fixed ramp held any healthy pool above about 1,000 proxies at pressure 1.00. It scores goroutines per proxy from 50 running proxies up, uses the absolute ramp for smaller pools, and no longer counts the direct transport as a pool member.
- **RAM detection ignored the unit's own cgroup limit** ([#698](https://github.com/full-bars/urnetwork-3.23-fix/pull/698), [#701](https://github.com/full-bars/urnetwork-3.23-fix/pull/701), [#702](https://github.com/full-bars/urnetwork-3.23-fix/pull/702)): it read `memory.max` at the mount root, which only exists in a container, so on a systemd host `MemoryMax=` and `MemoryHigh=` were never seen. It now walks the process's cgroup and its ancestors and takes the tightest limit. Pressure headroom follows the same rule, reclaimable page cache is no longer counted as used, and a limited level whose usage cannot be read reports headroom as unknown instead of borrowing an ancestor's room.
- **The OOM cap blamed this provider for other workloads** ([#705](https://github.com/full-bars/urnetwork-3.23-fix/pull/705), [#702](https://github.com/full-bars/urnetwork-3.23-fix/pull/702)): the host-wide `oom_kill` counter now gives way to the parent cgroup's hierarchical one when readable, an OOM kill restarts the clean-day clock in every branch, and a start marker older than 72 hours of silence is ignored, judged against an hourly heartbeat, so a kill after long uptime is still attributed.
- **GC settings were reverted or ratcheted** ([#698](https://github.com/full-bars/urnetwork-3.23-fix/pull/698)): the auto profile's GOGC was re-applied on every proxy launch, silently undoing the GC governor, and with self-heal off the governor could tighten but never release. The profile GOGC is now applied once per process, a persisted `set gogc` wins over the tier default, and every GOGC change is logged.
- **Concurrent log writers could lose lines** ([#705](https://github.com/full-bars/urnetwork-3.23-fix/pull/705)): `critLog` is serialized so two writers cannot both rotate `events.log`, and reload writes its `events.log` lines after releasing its lock so a slow disk stalls only that log tail.
- **Unreadable state was silently dropped** ([#705](https://github.com/full-bars/urnetwork-3.23-fix/pull/705)): an `oom_cap.json` or `run.marker` that exists but cannot be parsed now logs a warning instead of being treated as absent.
- **A slow give-up could mislabel a later genuine failure** ([#704](https://github.com/full-bars/urnetwork-3.23-fix/pull/704)): an attempt cut off by the connect deadline is reported as slow (`cut_short=true`) and no longer moves the shared auth rate limiter, so latency cannot spiral into a failure cascade. Each slow cycle restarts the retry ladder, the direct connection never queues behind slow or dead paid proxies, and a URL proxy that has never worked gets no amnesty from hanging until the deadline. The give-up line now reports the measured admission wait, attempt duration and raw error, and proxy-path symptoms (TLS handshake timeout, connection reset) are no longer blamed on API reachability.
- **Content-filtering blocklist refreshed** ([#697](https://github.com/full-bars/urnetwork-3.23-fix/pull/697), [#703](https://github.com/full-bars/urnetwork-3.23-fix/pull/703), [#717](https://github.com/full-bars/urnetwork-3.23-fix/pull/717)): the blocked-destination table is refreshed from upstream.
- **A hotswap could leave the audit trail without the new process's start entry** ([#670](https://github.com/full-bars/urnetwork-3.23-fix/issues/670)): the old process persists its own audit ring again at the end of its drain, up to 30 seconds after the new process merged and saved the combined ring, and that write can land last. The disk then held a ring without the new process's entries until the next control command more than 30 seconds after the last save, or a clean shutdown, so a crash in between lost them. The new process now waits out the drain, merges again and saves once more. This affects the audit trail only; traffic was never involved.
- **The pool controller sawtoothed on boxes with self-heal on**: after a pressure cut it regrew by 25 every five minutes until it hit the same wall, then shed again. It now remembers the pool size where pressure appeared and caps regrowth at 90% of it, relaxing back over 24 hours and then released, so a box whose capacity has changed can still find it. Pressure sheds rank by the persisted earnings score instead of lifetime traffic, which is empty right after a restart and made every proxy look idle, and the URL pool target is clamped to the running-proxy cap minus paid proxies, which the cap also counts.
- **The GC governor chased its own tail**: its 30 second sweep measured memory as `Sys` minus `HeapReleased`, which follows the heap goal, and the heap goal moves with the GOGC value the governor itself writes, so tightening lowered the reading and the next release tightened again. A box merely sitting at its soft limit also read as an emergency, which started the 10 minute pool cut. The sweep and the 10 second subtick now share one numerator, live heap plus goroutine stacks. The subtick also honours the CPU veto the sweep already had, and entering the critical level forces a full GC at most once per five minutes.
- **A draining proxy could recreate its own registry entry**: a late log line or dial after the proxy was unregistered created an address-less entry that nothing removes, inflating the proxy count and the goroutine-per-proxy divisor, OOM peak and headroom figures derived from it. Those two paths no longer create entries.

### Changed

- **A hotswap is declined when the box cannot hold two providers** ([#698](https://github.com/full-bars/urnetwork-3.23-fix/pull/698)): the candidate runs while the old provider drains, so both are resident. Available memory must be at least 1.1 times the running provider's RSS, otherwise the update falls back to a plain restart and the `urnet_hotswap_outcomes_total` label is `low_memory`. The check is bounded by the provider's cgroup headroom.
- **The per-proxy memory estimate now matches running nodes** ([#705](https://github.com/full-bars/urnetwork-3.23-fix/pull/705)): the startup warning was calibrated on freshly restarted providers and stayed silent on every node under real pressure. It will now fire on RAM-tight hosts with large pools. That is intended.
- **Capacity decisions reach the important buffer and the disk event log** ([#701](https://github.com/full-bars/urnetwork-3.23-fix/pull/701)): the trim receipt and result, the startup trim line, the `[oomcap]` decisions and the memory warnings are rare and are the only record of why a box ran fewer proxies. They used to go only to the RAM log, which floods and is wiped by a reboot.

## Deploy Notes

1. **Update and restart, no config changes.** `urnet-tools update` picks up the release. Nothing is enforced until you ask: the OOM cap stays in `shadow` and the smart dialer stays off.
2. **To turn the new behavior on.** `urnet-tools set oom-cap on` enforces the automatic start cap. `urnet-tools smart-dialer on` enables the measured-cost preference. Both are live and persisted. Read the decisions with `urnet-tools autopilot log`. The smart dialer is planned to become the default in a later release, after more testing, so enabling it on a few nodes now is the most useful thing you can do with it.
3. **Expect a lower pressure reading on large healthy pools.** The goroutine sensor now judges per proxy, so a healthy pool above roughly 1,000 proxies no longer sits at 1.00. It does not change what the actuators do at a given score, but the score itself moves, so on those nodes the things driven by it relax together: the per-connection memory budget returns to its unscaled size and probe concurrency rises. Memory use on a RAM-tight node with a large pool can go up, so update those nodes last and watch headroom.
4. **Expect a memory warning on RAM-tight boxes.** `[proxy][resources] warning` is advisory. Lower the pool with `urnet-tools proxy trim`, or raise the limit.
5. **HotSwap may fall back to a restart on a small box.** If available memory is under 1.1 times the running provider's RSS, the update restarts instead. See [HotSwap](../docs/HotSwap.md).
6. **Compatibility.** `ledger` is an additive control command, and an older provider answers `autopilot log` with an explanatory error. Run the matching provider and `urnet-tools`.
7. **The first start after this release** does not compare against an OOM marker written by older code, so it cannot produce a false attribution.
8. **The docs.** Log lines are in [LOG_REFERENCE.md](../LOG_REFERENCE.md), and the settings are in [Configuration](../docs/Configuration.md).
9. **The baseline recorder starts with this release.** It records from the first start of 32.8, so there is no earlier record on a box coming from 32.7 or older, and `baseline compare` becomes useful after the next upgrade, once each side has at least four samples past the post-restart ramp (about an hour of running at the defaults). To mark the boundary yourself, run `urnet-tools baseline mark "before 32.9"` just before updating. `urnet-tools set baseline off` stops it without a restart and keeps the file.
10. **Auto-profile tiers now follow the unit's own memory limit.** RAM detection walks the provider's cgroup and its parents, so a `MemoryMax=` or `MemoryHigh=` on the systemd unit is seen. A host with plenty of RAM but a lower limit on the unit selects a smaller tier under `URNETWORK_PROFILE=auto` (smaller receive queues, GOGC 50, a lower memory limit), and a startup line names the limit in force. If you rely on throughput, check `systemctl show -p MemoryMax -p MemoryHigh <unit>` on your nodes before updating.
11. **Be careful turning on the smart dialer on large pools.** Its background probes are real requests to the API, up to a couple per transport per proxy, spread over about a minute after start and not gated by the startup auth admission gate. On pools of hundreds of proxies, try it on one node first and watch for auth failures.
12. **Multi-container stacks share the new state files.** The documented multi-container stack mounts one `ur_config` volume on every node, and the 32.8 state files in it (`oom_cap.json`, the run marker, `baseline.jsonl`, `autopilot.jsonl`, `proxy_url.json` and `provider.sock`) are not per node. With the OOM cap in `shadow` this can only produce misleading attribution and baselines that mix nodes. With `oom-cap on` it could set a wrong cap, so give each node its own volume before turning it on. Per-node state is planned for the next release.
