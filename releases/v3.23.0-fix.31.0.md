# v3.23.0-fix.31.0

> [!NOTE]
> v3.23.0-fix.31.0 is a milestone release delivering architectural decoupling and operational high availability across the URNetwork Connect provider runtime. The flagship focus of this release is **Provider Daemonization**: a dedicated control-socket IPC plane, an offline pending-configuration queue, and consolidated systemd override keys, together with **Zero-Downtime HotSwap** for in-place binary updates and a round of **urnet-tools multi-provider UX smoothing**. Shipping alongside them are a heartbeat that names its own build and reports message-pool health in plain language, three fixes to RAM log integrity and volume, a port of upstream's lossy-carrier lane gating, and the repair of an update path that had been handing off to the binary it replaced. Rebuild and redeploy provider nodes, and update `urnet-tools` and `urnet-docker`, to adopt the new daemon architecture.
>
> The `v3.23.0-fix.31.1` through `v3.23.0-fix.31.9-rc1` tags were release candidates cut to exercise this work on a test node. They were never deployed, and they are published as prereleases, so the updater has never offered one to a fleet node. This is the release.

## 1. Overview & Highlights

- **Provider Control Plane & Daemonization (Flagship)**: Decoupled provider settings from brittle external file writes and process restarts into an in-process control state, with a local Unix domain socket (`~/.urnetwork/provider.sock`) as the live control plane and an offline fallback queue for seamless runtime reconfiguration.
- **Zero-Downtime HotSwap**: In-place binary handover between a running provider and a verified candidate, transferring the control socket and live listeners with a mandatory ACK-then-yield drain. Eliminates the standard 20–60s upgrade stall; the provider binary can be swapped with 0s downtime.
- **Control Socket IPC & Offline Pending Queue**: Replaces brittle systemd file edits and process restarts with a live control protocol (`urnet-tools set`). Settings changed while the provider is stopped or restarting are queued in `~/.urnetwork/pending_overrides.json` (flock-guarded across processes) and merged atomically on boot.
- **Systemd Key Convergence**: Migrates legacy `override.conf` keys (`URNETWORK_PROFILE`, `URNETWORK_RAMLOGS`, `GOMEMLIMIT`, `GOGC`) into the unified control-socket runtime state.
- **Public IP Autodetection & Dynamic Renaming**: Automatic detection of external IPv4 address via a cached background resolver with 60s TTL and concurrent-request deduplication; an operator can disable it with the `~/.urnetwork/disable_ip_autodetect` marker or `urnet-tools ip-detect off`. `urnet-tools rename` sets the dashboard display label without a restart.
- **urnet-tools Multi-Provider UX (One provider per OS user)**: `urnet-tools status`/`logs`/`summary` and `start`/`stop`/`restart` now resolve to the current OS user's provider by default and re-exec themselves under sudo for another user's provider; `providers` shows your providers and `providers --all` (as root) lists the whole box. `-y`/`--yes` aliases `--force`, `optimize` self-elevates and applies atomically, and manage-time refusals point at concrete next steps.
- **Settings Are Visible in the Provider Log**: `set`, `clear`, the startup merge of queued overrides, and dashboard-label changes now log at the provider, so an operator can confirm from the node that a change registered with the daemon instead of trusting the CLI's exit code.
- **JWT Auto-Refresh Transfer Stats Telemetry**: Step 3/3 of JWT rotation now parses `paid_bytes_provided` and `unpaid_bytes_provided` from `GET /transfer/stats`, reporting account balances inline in human-readable units (`unpaid: X, paid: Y`).
- **Android IPv6 ICE Egress Guard**: Synthetic IPv6 host candidates are gated behind `egressIPv6Usable()` send probes to prevent dead routes from blackholing cellular/VPN WebRTC traffic.
- **Automated CFAA Blocklist Synchronizations**: Continuous synchronization of Computer Fraud and Abuse Act IP blocklists with upstream definitions.
- **The Heartbeat Names Its Build and Explains Itself**: every five-minute tick now leads with `[health][build]`, carrying version, profile and node name, so a log tail or a pasted excerpt can be tied to a build after the startup banner has scrolled away. The message-pool line alongside it reports a plain-English verdict (`ok`, `warming`, `watch`, `leak`) rather than a return percentage that cannot detect the leak it exists to catch.
- **RAM Log History Is Actually Preserved**: the five-second trimmer had been overwriting the history it claimed to keep with NUL padding since the day it was written. Both the main and the important buffer are fixed, and `urnet-tools logs` now follows where the provider actually writes rather than where stored state says it should.
- **Updates Land on the Binary You Installed**: HotSwap resolved its own image by inode, so once the updater moved the running binary aside it handed off to the backup, reported success and changed nothing. Version resolution on stripped release builds is fixed alongside it.
- **Lossy Carriers No Longer Stall the Reliable Lane**: upstream's WebRTC lane-gating fix is ported, so a full unreliable resend queue stops collapsing throughput while a reliable relay lane sits idle.
- **The Provider Is the Single Source of Truth for Settings**: a v2 config schema records where every setting came from, socket, environment, pending queue, legacy file or default, and `urnet-tools config` shows it. An operator whose setting appears not to have taken can see which of five writers won instead of guessing.
- **Prometheus `/metrics`**: eleven `urnet_*` metrics covering the proxy pool, per-proxy traffic, errors, contracts and the Go runtime, with no new dependencies, toggleable live.
- **Control Socket Hardening**: peer credential checks, a read deadline, request and value size limits, and protocol version negotiation, so filesystem permissions are no longer the only gate on the settings plane.
- **Phased Startup Banner**: boot messages collected into phases with per-phase results, closed by a single `Ready` line carrying version, profile and proxy count.
- **Conntrack Tuning in `optimize`**: `nf_conntrack_max` was never set at all, leaving the 65,536-entry kernel default on boxes carrying thousands of proxy connections. It now scales to host RAM.
- **`urnet-tools proxy ids`**: shows the `client_id` the platform assigned to each proxy, including the direct transport.

## 2. Provider Control Plane & Control Socket

### Control Socket
The provider owns a single Unix domain socket at `~/.urnetwork/provider.sock` (owner-only 0600) through which `urnet-tools` sends live `set`/`clear`/`get` commands. There is no Windows named-pipe transport — the provider listens on a Unix domain socket on all platforms the provider runtime supports.

- **Single owner, single writer**: the provider process is the only writer of `~/.urnetwork/provider_state.json` (atomic temp-file + rename). The socket is how `urnet-tools` safely asks it to change a setting, instead of two processes editing a shared override file.
- **Cross-process safety**: both the Go CLI and the install script's shell helpers flock `pending_overrides.json.lock` (and the provider adopts it during merges), so a queued override written while the provider is mid-startup can never be dropped.
- **Atomic set/clear**: a socket `set`/`clear` runs its read → apply → persist → rollback as one locked unit, so concurrent connections cannot interleave and clobber each other or leave memory and disk disagreeing.

### Offline Pending Configuration Queue
When an operator issues a configuration command while the provider is offline, `urnet-tools` persists the instruction to `~/.urnetwork/pending_overrides.json`:
- **One-Shot Startup Consumption**: on boot the provider merges the queue atomically, applies runtime side effects (memory limits, GC percentage), and clears the file.
- **Zero Configuration Drift**: eliminates race conditions between configuration tooling and the service supervisor startup hook.

### Unified Configuration, v2 Schema (#575)

The provider becomes the single source of truth for every setting. The state
file gains a v2 envelope, backward compatible with v1, and each setting records
where it came from: the control socket, the environment, the pending queue, a
legacy state file, or the built-in default. A `status` socket command returns
all of it with that source metadata, and `urnet-tools config` renders it as a
table or as JSON.

Source tracking is what makes the rest of the surface debuggable. An operator
who sets a profile and sees the old one still in effect can now see which of
five writers actually won, rather than guessing. Mutation goes through a single
API so the value and its metadata cannot drift apart, and persistence syncs both
the file and its parent directory.

### Server-Side Validation and Restart Flagging (#566, #572)

Validation existed only in the client, so anything writing to the socket
directly could persist a value that silently broke the provider on its next
start. The server now validates all fourteen keys itself, accepting `v4` and
`v8` as aliases for the turbo profiles the way the CLI already did.

Each `set` and `clear` response also carries a `needs_restart` flag, computed
from whether the key has a live side effect rather than from a hand-maintained
list. Adding a new live-applied key requires adding its case and nothing else,
so the flag cannot go stale. `urnet-tools set` prints the warning when it comes
back true.

### Systemd `override.conf` Migration
Configuration keys previously requiring static systemd drop-ins are now managed directly through the control socket:
- **`profile` & `ramlogs`**: seeded into the early execution environment before logging initialization.
- **`gomemlimit` & `gogc`**: applied dynamically via Go runtime debug APIs (`debug.SetMemoryLimit`, `debug.SetGCPercent`) both on boot and during live operation.

## 3. Zero-Downtime HotSwap

HotSwap is fully implemented in this release (not a later milestone): the provider can hand off live service to a verified candidate binary without cycling the unit.

- **Candidate pre-flight**: the candidate verifies its tokens, DoH, and API reachability before taking over, then announces READY.
- **Listener & state handover**: the active control-socket listener and coordinator session are yielded to the promoted candidate only after it confirms a mandatory TAKEOVER ACK — there is never a window where neither process holds them.
- **Graceful drain**: the retiring process stops accepting new work, flushes retained events, and exits once the candidate is live.
- **SIGUSR2 trigger**: `urnet-tools hotswap` / a HotSwap-capable `urnet-tools update` signals the running provider (version-gated to avoid signaling a pre-HotSwap binary). Docker providers do an in-place PID-1 `syscall.Exec`; systemd providers use `Type=notify` handoff and `NOTIFY_SOCKET` isolation.
- **Automatic rollback**: `urnet-tools update` rolls the on-disk binary back if the candidate fails to take over, and never claims "live provider retained" after ownership has actually transferred.

> [!IMPORTANT]
> **HotSwap ships dormant on every systemd node, and reinstalling does not
> change that.** The handoff transfers `MainPID`, which needs `NOTIFY_SOCKET`,
> which systemd only provides to a `Type=notify` unit. The installer
> deliberately writes `Type=simple` and does not offer `Type=notify` at all.
>
> That is not an oversight. `Type=notify` makes `systemctl start` block until
> the provider sends `READY=1`, and the provider only sends it once a proxy or
> the direct path has brought up a transport. That wait is unbounded: the
> per-proxy auth retry backs off legitimately for hours against a rate-limited
> or unreachable API, and a provider with direct disabled and no proxies
> configured never sends it at all. The unit and the binary also ship through
> different channels, the unit from git and the binary from a release, so any
> skew pairs a `Type=notify` unit with a binary that has no `sd_notify`
> support and every start hangs forever. That combination wedged the
> pre-release shakedown for two hours until the CI watchdog killed it.
>
> On every systemd node `urnet-tools update` detects the unit type, declines
> HotSwap with an operator message, and falls back to a normal restart, so
> updates keep working with the usual 20-60s stall. The gate fails closed on
> both sides: the tool declines before signalling, and the provider aborts the
> handoff rather than corrupting `MainPID`.
>
> **Where HotSwap does work today: Docker**, where the provider is PID 1 and
> re-executes in place, with no systemd readiness contract involved.
> Zero-downtime updates under systemd need the readiness problem solved
> first, which is not in this release.
>
> This gate is deliberate and fails closed. An earlier revision gated only on
> the version string, so `triggerHotSwap` fired, the internal handoff silently
> aborted, and the "hotswap triggered" path skipped the restart fallback
> entirely, turning every update on a pre-existing node into a permanent no-op.
> Losing zero-downtime is always the safer of the two failure modes.

### HotSwap Handed Off to the Wrong Binary (#588, #594)

HotSwap resolved the image to spawn with `os.Executable()`, which reads
`/proc/self/exe` and follows the inode rather than the path. The update flow
installs the new build at the provider's binary path and moves the running one
to a backup, so from that moment `os.Executable()` names the backup. The handoff
spawned it: the old build came up, announced READY, the parent drained and
exited, and the operator watched a clean zero-downtime swap that changed nothing.
`updateProvider` prefers HotSwap and skips the unit restart when the trigger
succeeds, so the fallback that would have worked was bypassed precisely because
the handoff "worked".

> [!NOTE]
> Not a regression. This is how HotSwap has resolved its own image for as long
> as it has existed. It stayed invisible because post-update verification does
> eventually catch the version mismatch, roughly eighty seconds later, and
> reports it as the candidate failing to take over.

The install path is now captured at init, while it still names the installed
file, and that is what the handoff spawns. An unusable path aborts rather than
falling back, the candidate is validated as a regular executable file rather
than merely existing, and the ` (deleted)` suffix the kernel appends to an
unlinked image is stripped. Permission checks moved to `syscall.Access(X_OK)`,
which asks whether this process may execute the file rather than inferring it
from mode bits, and are gated off on Windows where POSIX bits are never set.

> [!IMPORTANT]
> A provider whose binary predates this fix cannot be upgraded by HotSwap,
> because the broken resolution is in the retiring process. Restart the unit
> once to get onto a fixed build. HotSwap works normally from there.

### Version Resolution on Release Builds (#578, #579, #580, #585, #587)

Release binaries are built with `-trimpath`, which strips `-ldflags` out of Go
build info, so `main.Version` cannot be read back out of a release binary at
all. Every consumer of a provider's version sat on that one broken source, which
is why HotSwap had never engaged on a release build: the preflight read an empty
version, declined with a reason naming a version that was never the problem, and
returned before the unit-type check ever ran.

Three sources now answer the question, in the order of how directly they know it:

1. **The running provider's control socket** answers a `version` request with
   its own build string (#580). This is the only source reporting what the
   process *is* rather than inferring it from the filesystem, so it is asked
   first. A provider built without `-ldflags` answers `dev`.
2. **A greppable stamp in the binary's data segment** (#579). `-trimpath` strips
   build info but not program data, so the release workflow embeds
   `URNET_VERSION_STAMP=<version>` as a plain string literal and the tool scans
   for it without executing the file. This works on a stopped provider, a
   cross-architecture binary, and any release build. It is also what lets a
   v30.9 tool verify an upgrade to v31 at all.
3. **`/proc/<pid>/exe`, then on-disk build info** (#578), for providers too old
   to know the socket command. Reading through `/proc` matters because `update`
   swaps the binary before the HotSwap preflight runs, and on Linux a rename
   over a running binary leaves that path naming a deleted file.

> [!NOTE]
> Not a regression, and no production node was affected. HotSwap was introduced
> on the v31 line, which has never shipped, and had never worked in any build of
> it including every release candidate.
>
> These two defects are sequential, not alternative. Before #578 the preflight
> read an empty version and declined, so the handoff never ran at all. Fixing
> the version read let it engage for the first time, and engaging is what
> exposed #588, where it spawned the binary the updater had moved aside. The
> second was only reachable once the first was fixed.

Two further holes closed after that:

- Go 1.27 with `-trimpath` emits `v0.0.0-<ts>-<hash>+dirty` in build info. The
  pseudo-version filter rejected `+incompatible` but not `+dirty`, so the
  garbage version passed as real, short-circuited the stamp scan, and
  `hotSwapVersionOK` declined a perfectly good candidate (#587).
- `confirmGateMulti` printed an empty version whenever the in-memory provider
  struct had not been populated; it now falls back to reading the binary (#585).

Unattended timer updates also record the version that was running before the
swap, so the audit trail says what was replaced rather than only what replaced
it (#584).

## 4. Node Identity, Telemetry & Operator Tooling

### Public IP Autodetection & Dashboard Display Label (PR #534)
- **Automatic IPv4 Discovery**: resolves the provider's public egress IP at boot and on a 60s TTL, automatically appending `@ <RedactedIP>` to the dashboard identity string.
- **Concurrent Request Deduplication**: only one external fetch runs per TTL window; concurrent callers share the in-flight result or the cached value.
- **Operator Opt-Out**: creating `~/.urnetwork/disable_ip_autodetect` or running `urnet-tools show-ip off` disables public IP querying (there is no `--disable-ip-autodetect` flag).
- **Dynamic Node Renaming**: `urnet-tools rename <name>` sets the dashboard display name without modifying the hostname or restarting the service.
- **Command renamed**: the toggle is `urnet-tools show-ip [on|off|status]`. It was `ip-detect`, which named the mechanism rather than the effect and read as a diagnostic that would report the IP; it also sat awkwardly next to `direct`, which is about the address the provider *serves* on. `ip-detect` and `ipdetect` remain as aliases.

### urnet-tools Multi-Provider UX (one provider per OS user)
The tool now treats the OS user as the primary implicit scope:

- **Implicit current-user scope**: an unprivileged `urnet-tools command` with no target resolves to the provider owned by the current OS user, silently. Other users' providers are not enumerated on every command.
- **`providers` / `providers --all`**: the one place multi-user inventory lives. `providers` lists your providers; `providers --all` (as root) lists every provider on the box.
- **Cross-user self-elevation**: targeting another user's provider (`status --user bob`, `start --unit <unit>`) re-executes the command under `sudo <full binary path>` — so the binary-on-a-per-user-path problem never surfaces as a "command not found" or a manual `sudo /long/path` hunt. `start`/`stop`/`restart` carry `-f`/`--yes` through so the elevated child doesn't re-prompt; a dry run never elevates.
- **`-y`/`--yes`**: aliases `--force` — `urnet-tools restart -y` skips the confirm prompt just like `-f`.
- **`optimize` self-elevates and is atomic**: `urnet-tools optimize` re-executes under sudo with its own resolved binary path, snapshots the current sysctl values, applies the live set, persists `/etc/sysctl.d/99-urnetwork.conf`, and rolls the live keys back on any failure — no more half-success ("settings are live but will not survive reboot") and no `sudo urnet-tools` "command not found".
- **Actionable manage-time refusals**: when more than one provider is in scope and no target is given, the refusal points at `--unit`, `default set --network <name>`, and `providers --all` instead of a manual sudo hunt.
- **Control-socket liveness in `status`**: the status output reports whether the provider's control socket is actually bound — a running PID can exist with no reachable socket (startup failure or a same-user collision).

### Settings Are Visible in the Provider Log
A setting that reaches the running provider now says so in the provider's own log, so an operator can confirm from the node that the daemon registered the change rather than trusting the CLI's exit code:

```text
⚙️ [control] set profile=v8 (was unset)
⚙️ [control] cleared gogc (was 200)
⚙️ [control] applied 2 queued override(s) from pending_overrides.json: profile=v8, cleared gogc
🏷️ [identity] dashboard label changed: nyc-1 [...] -> nyc-2 [...]
```

- Rejected changes and "persisted but could not apply live" both log, since a refused change is when the log most needs to explain itself.
- `get` stays silent: `urnet-tools status` polls it on every invocation.
- `rename` and `show-ip` never touch the socket (they take effect at the next renewal), so the dashboard label is logged on first resolve and on every change. It is not logged per call, because `providerDescription` runs once per proxy per renewal.

### JWT Auto-Refresh Transfer Stats Telemetry
- **Inline Accounting Output**: during step 3/3 of JWT rotation, the verification response from `GET /transfer/stats` is parsed for `paid_bytes_provided` and `unpaid_bytes_provided`:
  ```text
  🔑 [jwt] refresh → step 3/3: verifying new token against https://api.bringyour.com/transfer/stats...
  🔑 [jwt] refresh → step 3/3 ok: verification passed (HTTP 200, unpaid: 500.0 MB, paid: 1.0 GB)
  ```
- **Robust Error Handling**: JSON parsing errors or schema variations fall back gracefully to status-code reporting without interrupting token renewal.

### Prometheus `/metrics` Endpoint (#565, #568)

A Prometheus text-format endpoint for fleet-wide monitoring, with no new
dependencies: the format is generated directly. It mounts on the loopback
diagnostics server, and `URNETWORK_METRICS` binds it on the Tailscale address
for remote scraping. `urnet-tools metrics on|off` toggles it on a running
provider without a restart.

| Metric | Type | Labels |
|---|---|---|
| `urnet_uptime_seconds` | gauge | |
| `urnet_connections_active` | gauge | |
| `urnet_proxy_pool_size` | gauge | `status` = up, dead, degraded, connecting |
| `urnet_proxy_bytes_total` | counter | `proxy`, `direction` = in, out |
| `urnet_proxy_clients` | gauge | `proxy` |
| `urnet_errors_total` | counter | `category` = transport, ip, proxy, webrtc |
| `urnet_contracts_total` | counter | `result` = acquired, denied |
| `urnet_gc_cycles_total` | counter | |
| `urnet_mem_heap_bytes` | gauge | |
| `urnet_mem_sys_bytes` | gauge | |
| `urnet_goroutines` | gauge | |

Bind it with `URNETWORK_METRICS`, for example `192.200.0.5:9100`. Always give
it an explicit address. A bare port such as `:9100` binds every interface,
which on a public host publishes per-proxy traffic detail, client counts and
error metrics to the internet. The endpoint has no authentication of its own,
so the bind address is the only access control it has.

### Configuration and Audit Commands (#568, #575)

- **`urnet-tools config`** shows every setting with the source it came from,
  as a table or as JSON. See the unified-config section above for why the
  source matters.
- **`urnet-tools history [limit]`** reads the provider's 1000-entry circular
  command audit ring, last 50 by default and 100 at most.
- **`urnet-tools profile [name]`** shows or sets the memory and GC tuning
  profile, and with no argument explains what each one is for.
- **`urnet-tools dashboard`** is a terminal status panel covering state, active
  settings, proxy sources and restart warnings. Aliases `dash` and `panel`.

### Phased Startup Banner and Ready Summary (#571, #577)

Startup messages were scattered through the boot path in the order the code
happened to run. They are now collected into phases, system audit, logger,
identity, control state, proxy load and status server, each reporting its own
result, showing timing when it exceeds 100 ms and marking warnings inline. A
single `✅ Ready` line closes the sequence with version, profile and proxy count.
The banner suppresses itself under systemd, where `INVOCATION_ID` is set, and
`URNETWORK_STARTUP_BANNER=0` turns it off anywhere.

Three logging defects were fixed alongside it (#577):

- **The startup banner printed twice**, because the RAM-log initialiser ran from
  both `initGlog` and the handover path. Guarded with a `sync.Once`.
- **Idle log spam**: the lifetime, earnings and profit lines re-emitted
  identical data every minute on an idle node. They now emit on a value change
  or an idle-to-active transition.
- **The RAM-log redirect countdown was invisible**, because the auto profile set
  `URNETWORK_RAMLOGS=1` before glog initialised, so the 3-2-1 was already going
  to `/dev/shm`. The environment write moved after the countdown.

### The Heartbeat Names Its Build (#595)

The five-minute heartbeat block carried no version anywhere. On a busy node the
startup banner scrolls out of the RAM log window within minutes, so a tail or a
pasted excerpt could not be tied to a build. `[health][build]` now leads every
tick:

```text
🏷️ [health][build] v3.23.0-fix.31.0 profile=turbo-v8 host=node-a
❤️ [health] uptime=5m0s profile=turbo-v8 heap=19MiB sys=46MiB goroutines=717 connections=0 proxies=26
❤️ [health][pool] warming — 88 buffers in use, 174 allocated since start (99.73% returned). Stuck-buffer check needs 1h of uptime (55m to go).
```

### Message-Pool Health in Plain Language (#592, #595)

The heartbeat gained an aggregated message-pool line. Its first draft led with
`return=99.65%`, which is the one number that cannot detect the leak the line
exists to catch. A leak proportional to throughput holds returned-over-taken
near 100% forever, because the denominator grows exactly as fast as the leak:
one buffer lost per ten thousand taken reads 99.99% while shedding well over a
thousand a day.

The line now leads with a verdict word and the numbers that can actually move
under a leak, the outstanding low-water mark and the all-time allocation count.
Four states are possible, `ok`, `warming`, `watch` and `leak`. The floor
tracking needs an hour of uptime before it can distinguish a leak from normal
churn, which `warming` says outright with a countdown rather than reporting a
clean bill of health it has not earned. `LOG_REFERENCE.md` documents all four
with worked examples.

### `urnet-tools proxy ids` (#593)

Shows the `client_id` the platform assigned to each proxy, including the
`direct` transport, read from the provider's local client-JWT store. The bearer
tokens in that store are never printed.

### systemd STATUS= Reflects Proxy Reality (#591)

`systemctl status` reported `starting: resolving proxies` forever when the proxy
source was broken, because no state existed for "tried and failed", and it
carried a configured count fixed at startup that no reload ever updated. Reloads
now publish the configured count and a resolution state, a failed or empty fetch
publishes the failure with its reason, and a source yielding nothing usable
emits a rate-limited operator warning. These counters are operator-facing only.
No control flow reads them, and READY stays decoupled from health.

## 5. Security & Platform Hardening

### Android IPv6 ICE Egress Guard
- Dialing synthetic IPv6 interfaces on Android previously succeeded on connect-only UDP dials due to default cellular routes, but blackholed traffic once outbound packets traversed the VPN tunnel.
- ICE host candidates are now guarded by an explicit `egressIPv6Usable()` send probe, preventing Pion WebRTC from advertising unreachable IPv6 routes and stalling ICE negotiation.

### Conntrack Tuning in `optimize` (#569)

`nf_conntrack_max` was never set at all, leaving the kernel default of 65,536
entries on boxes carrying thousands of proxy connections. `optimize` now scales
it to host RAM across six brackets, from 131,072 below 1 GB to 4,194,304 above
32 GB, and cuts `nf_conntrack_tcp_timeout_established` from the kernel default
of five days to one hour. Skipped cleanly when the module is not loaded, and
persisted to `/etc/sysctl.d/99-urnetwork.conf` with rollback.

The one-hour established timeout is deliberate. A proxy node opens and drops
connections constantly, and at the kernel default of five days the table fills
with entries for peers that are long gone, which is what exhausts it. Reaping
idle entries after an hour is what keeps a raised `nf_conntrack_max` from
simply filling up more slowly.

> [!NOTE]
> Both settings are host-wide, not per-process, and persist across reboots via
> `/etc/sysctl.d/99-urnetwork.conf`. On a node that also carries long-lived
> idle connections without TCP keepalives, such as a persistent SSH session or
> a database connection, those can be reaped after an hour. Enable keepalives
> on such connections, or raise the timeout back, on a box that is not a
> dedicated provider.

### Control Socket Hardening (#573)

Defense in depth on the Unix control socket, which carries settings changes and
is owner-only by permission alone:

- **Peer credential check on Linux**: `SO_PEERCRED` verifies the connecting UID
  matches the provider's, so filesystem permissions are no longer the single
  gate.
- **Five-second read deadline per line**, which closes the slowloris shape where
  a connection is held open without ever completing a request.
- **Size limits**: 64 KiB per request, 4 KiB per value.
- **Version negotiation**: `v=1` is current, `v=0` is accepted as legacy, and
  anything higher is rejected rather than parsed hopefully.

### Automated CFAA Blocklist Synchronization (PR #540, #542)
- Synchronized Computer Fraud and Abuse Act IP blocklists with upstream definitions:
  - PR #540: Updated IPv4 definitions to 43,479 entries and IPv6 to 438 entries.

## 6. Transport & Transfer

### Lossy Carriers No Longer Stall the Reliable Lane (#586)

Ports upstream's WebRTC lane-gating fix to the fork. When a lossy carrier filled
the resend queue, the entire send sequence stalled even with a reliable relay
lane sitting idle, the throughput collapse operators saw as 1 Mb/s falling to
zero. The unreliable flight limits are now decoupled from the global
resend-queue gate: with a reliable route available, overflow writes bypass the
unreliable flight and route to the reliable lane instead. Acknowledgement RTT
samples carried over unreliable transports are excluded from the RTT window, so
fast datagrams no longer drag the scaled retransmission timeout down to its
floor. ICE UDP connections get a 4 MB socket buffer.

The upstream change targets a different code layout, so the port adapts it to
the fork's flat resend-queue model rather than carrying over a scheduler the
fork does not have. Running it live surfaced three further defects, all fixed
here:

- **Flight reserve stranded on zero-byte acknowledgements**: the release path
  sat behind a byte-count guard while the grant path ran before it, so an
  acknowledgement carrying no bytes took a reserve permanently out of
  circulation.
- **Message-pool double return**: the multi-route writer documents that on any
  failure the frame has already gone back to the pool. The port added a second
  return on failure paths in two write helpers. The helpers now own the frame on
  every path, and only the one case where no writer ever took it returns it.
- **nil-map panic in route selection**: a shadowed declaration inside the
  cache-miss branch left the outer variable holding the nil map from the failed
  lookup. The shadowing long predates this work and was unreachable while
  transport entries were never deleted. This change deletes them when empty,
  which reached it.

Measured on a test node before and after, same box and same traffic profile: the
pre-fix build logged 561 pool warnings and 10 panics over 51 minutes; the fixed
build logged none of either.

## 7. Log Integrity & Volume

### The RAM Log Trimmer Was Overwriting History With NUL Padding (#596)

The five-second trimmer bounded the log by copying out the newest two thirds,
truncating, and writing that portion back. It read with `ReadAt` on a descriptor
opened write-only, so the read always failed with `EBADF`. The error was
discarded and the freshly allocated, zero-filled buffer was written back as the
"preserved" history.

> [!NOTE]
> Not a regression. This has been the behavior since the trimmer was added, and
> no test ever covered it. The existing tests all cover the tail hint instead.

Both buffers are affected. The important buffer exists so the earnings and
health signal survives for hours after an incident, and it was 97% padding.
Measured on a live node before the fix, the main log carried 3.5 MB of NUL bytes
before the first real line. The descriptor is now opened read-write and a read
failure aborts the trim rather than being written back over good data.

### `urnet-tools logs` Followed Stored State, Not the Provider (#597)

The RAM-log decision was made from the control-state chain alone: control
socket, then the pending-overrides queue, then the legacy state files. The
provider decides from `URNETWORK_RAMLOGS` in its own environment. Deciding only
from stored state guarantees the two disagree whenever the variable arrives by
another route, an `Environment=` line in a unit body, a drop-in, an
`EnvironmentFile=`, or a container started with `-e`. The symptom was `logs`
streaming an almost-empty journal while the provider appended to `/dev/shm`
twice a second. The shell installer already greps drop-ins for exactly this key,
so the two halves of the tooling disagreed with each other as well.

### Two Unthrottled Error Lines (#598)

Both dominate the RAM log window on a busy node, and both are the same class of
defect already fixed for `[t]auth error` and `[contract]oob err`.

| Line | Measured rate | After |
|---|---|---|
| `completeHandshake failed: tls handshake timeout` | 487 lines in 6m25s on a node with 1160 proxies | 1/min per reason class |
| `[c]audit send error` | 94 lines in 27 min on a 30-proxy test node | 1/min |

The handshake line is keyed on the reason class, timeout against canceled
against deadline, rather than the client id. A per-client throttle would still
emit a thousand lines a minute on a busy box, which is no throttle at all. Each
carries an `(N suppressed)` count since the last emission, and the first
occurrence in a session always logs cleanly.

This matters more now that the trim fix actually preserves history: once
history survives, log volume is the only thing setting how far back the window
reaches.

## 8. Fixes in This Release

Beyond the feature work above, this release closes a set of defects found while
hardening the v31 surface for release.

- **systemd `Type=notify` no longer wedges every start and restart (#546)**: the provider sent `READY=1` only once a proxy had authenticated, so under a `Type=notify` unit systemd waited on a readiness signal that arrived late or never, and `systemctl start`/`restart` hung. READY is now sent when the provider is self-managing, not when a proxy authenticates (#543, #546).
- **Provider version resolves on `-trimpath` release builds (#547)**: `urnet-tools` could not read the version out of a stripped release binary, so `urnet-tools update --tag` reported the wrong version and refused to align an install to a requested release.
- **HotSwap no longer reads a childless session as a dead candidate (#552)**: the drain-liveness monitor armed unconditionally, but `Wait` returns immediately when no child process backs the session, leaving that select case and `ctx.Done()` both ready. Go chose between them at random, so a handoff that in fact succeeded could report a dead candidate and exit non-zero.
- **Profile defaults no longer clobber persisted `gomemlimit`/`gogc`**: applying a profile overwrote values an operator had set explicitly.
- **Installer `json_escape` emitted unquoted JSON**, corrupting `pending_overrides.json`, and queueing under `sudo` left the file owned by root.
- **Non-provider siblings no longer appear as phantom providers (#599)**: discovery treats any `urnetwork-*` systemd unit as a provider candidate, and falls back to that name match when `ExecStart` cannot be read. An unrelated unit such as `urnetwork-rebind-<name>.service` then showed up as a second provider and made every command on a single-provider box ambiguous. A name-only match now also needs a `.urnetwork` state directory as corroborating evidence; without a resolvable provider binary or a state directory the unit is rejected.
- **The weekly auto-update timer had never completed an update (#581)**: its `ExecStart` is a bare `urnet-tools update`, systemd hands a oneshot unit `/dev/null` on stdin, and the version-choice prompt was gated only on `!force`, so the non-terminal read was refused and the unit exited 1 on every run. `runUpdate` already computed an interactive decision for the target pickers and the two confirmation gates ignored it, so one run could skip the picker as non-interactive and then demand a prompt anyway. `unattendedUpdate()` makes it a single decision read by all of them: `-f`, a systemd `INVOCATION_ID`, or stdin on `/dev/null` all skip prompts, while non-interactive stdin that is not `/dev/null` still refuses, so a pipe or an SSH session without a pty cannot silently auto-confirm. An flock serialises concurrent updates of the same binary. Not a v31 regression; the install script has written that same `ExecStart` since before v3.23.0-fix.30.9, so every node it has provisioned is affected.
- **A sentinel-update unit showed up as a provider (#576)**: the non-provider suffix check missed `-sentinel-update`. Stopped units with no resolvable binary now display as such rather than as a provider with no version.
- **The HotSwap decline reason was lost on the update path (#560)**: an update that fell back to a restart no longer reports the fallback without saying why HotSwap declined.
- **Discovery corroborates units against `ExecStart` (#562)**.
- **Profile commands with no arguments print the current status (#564)** instead of treating the empty argument as an error.
- **The update timer's unit says what it means (#583)**: the code fix that makes a bare `urnet-tools update` work under systemd landed separately, but the unit's `ExecStart` now passes `-y` so the non-interactive intent is explicit in the file an operator reads.

## 9. Release Engineering

Not user-facing, but it is why this release is testable.

- **Pre-release shakedown sections Q-Z (#544)**: a battery covering the v31 daemon surface specifically, including hotswap decline and engage, failure injection, a low-memory sweep and multi-provider on one box.
- **Docker Shakedown workflow (#545)**: the same treatment for the container surface.
- **The shakedown ran to completion for the first time (#550)**: section L read a variable that was never assigned, and under `set -u` that aborted the suite silently at that point. Every section after L had therefore never executed in any run. Both shakedown workflows now surface the script's raw output on failure and warn when a report ends without a SUMMARY, so a truncated run cannot read as a completed one.
- **CI wall clock cut roughly in half (#551)**: the race suite is sharded across three runners, lint runs beside the tests rather than behind them, the test retry no longer masks genuine failures by retrying them, and the three workflows that lacked concurrency groups got them.
- **Manual shakedown dispatch can target a specific release (#548)**, so a fix can be verified without cutting a new tag.
- **Shakedown failures across four surfaces (#558)**: Docker architecture selection, `--tag` handling, restart verification and hotswap.
- **Docker shakedown raced the image (#555)**: the workflow pulled before the image was published.
- **Review findings on both shakedown workflows (#557)**.
- **An exec race in the discovery fallback test (#559)** and **an auto-update test that mutated the host (#563)**.
- **A test that passed only in CI (#589)**: `TestCurrentProviderNetworkID` pointed `HOME` at a temp directory, but the global client-JWT store is a package-level variable initialised at load time from the real home directory, so the fallback returned the developer's own network id instead of the empty string the case asserts. It failed on any machine that had ever run a provider and passed on a fresh runner. Test-only change.
- **`sn-status` returned success when every call failed (#590)**: `FetchSnStatus` always returned a nil error, so a total outage surfaced as seven zero-value assertion mismatches rather than a failure. It now returns an error when both independent API calls fail, while preserving whatever was partially retrieved. The accompanying flake had three causes: the shared 15-second budget across three calls is now a per-call 10-second budget, and the tests use a direct-only client strategy rather than paying DNS resolution against a local test server.

## 11. Deployment & Upgrade Instructions

> [!IMPORTANT]
> - **Provider Nodes**: rebuild and deploy provider binaries to pick up the control socket listener, pending override integration, public IP autodetection, HotSwap handoff, and inline transfer stats reporting.
> - **CLI Management**: upgrade `urnet-tools` alongside the provider binaries to get the control socket client, pending queue, `-y`/`--yes`, and cross-user `sudo` self-elevation. `urnet-tools update` refreshes the tool from the same release.
> - **Docker Deployments**: pull `ghcr.io/full-bars/urnetwork-3.23-fix:v3.23.0-fix.31.0`.

> [!WARNING]
> **The first upgrade onto this release must be a restart, not a HotSwap.** The
> image-resolution bug fixed in #588 lives in the retiring process, so a
> provider running any earlier build hands off to the binary it just replaced
> and reports success.
>
> There is no flag that declines HotSwap. `update` attempts it whenever the
> provider is running, so the only way to avoid it is to update while the
> provider is stopped:
>
> ```
> urnet-tools stop
> urnet-tools update
> urnet-tools start
> urnet-tools version     # confirm the new version is live
> ```
>
> This is not a HotSwap workaround you will later stop needing. On a systemd
> node HotSwap is declined every time, so `update` already falls back to a
> restart on its own. Stopping first only removes the wasted attempt and makes
> the outcome unambiguous.

> [!IMPORTANT]
> **Nodes on v3.23.0-fix.30.9 will report a false "failed to update" even when
> the upgrade succeeds.** On those builds, resolving a running provider's
> version falls through to reading `-ldflags` out of Go build info, which the
> `-trimpath` release build strips, so the read comes back empty. The
> post-update verification cannot confirm the new binary took over and reports
> the update as failed. Measured on a test node: the restart had taken effect,
> the process id had moved and the unit was active, while the run printed
> `1 of 1 provider(s) failed to update`.
>
> The same blind spot defeats the "already on `<tag>`" skip check, so a node
> can reinstall the same release repeatedly.
>
> This is fixed by the version-stamp and control-socket work in this release,
> but the build doing the upgrading predates the fix. **Verify the outcome with
> `urnet-tools version`, not the exit status of `urnet-tools update`.** Once a
> node is on this release the reporting is correct.

> [!WARNING]
> **Do not expect zero-downtime updates on a systemd node in this release, and
> do not reinstall hoping to get them.** The installer writes `Type=simple` on
> purpose, so HotSwap is declined on every systemd node and `update` falls back
> to a restart. See the HotSwap section above for why that gate exists and why
> `Type=notify` was rejected.
