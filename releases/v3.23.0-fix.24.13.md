## Installing / Updating

**Binary (bare metal / VM) — Fresh install:**
```sh
curl -fSsL https://raw.githubusercontent.com/full-bars/urnetwork-3.23-fix/refs/heads/main/scripts/Provider_Install_Linux.sh | sh -s -- install
```

**Updating an existing install:**
```sh
urnet-tools update
```

**Docker:**
```sh
docker pull ghcr.io/full-bars/urnetwork-3.23-fix:v3.23.0-fix.24.13
```

## What's New

### `urnet-tools update` bootstrap self-update — finally fixed

v3.23.0-fix.24.12 shipped the fix (tarball-bundled script + GitHub fetch), but it had a **chicken-and-egg problem**: the fix lived in the script determination code, but the old script (which runs the update) never reaches that code — it just does `cat "$0"` (reads itself from disk). So the fix couldn't propagate to existing installs.

**v24.13 fixes the bootstrap**: a check for the tarball-bundled `urnet-tools` is placed in the **common script-writing section** — the code that runs after `cd "$workdir"` and before writing the script to disk. Every old script has this code. So even the oldest script, after downloading the v24.13 tarball, will find the bundled script at `$workdir/urnet-tools` and install it.

This means:
- **The fix works on the very first update from any previous version** — no need for manual script replacement
- **`-f` restart-logic propagates** because the new script's `stop_systemd_units` + `install_systemd_units` handle it correctly
- **Future updates from v24.13+** work without any bootstrap issues

### `urnet-tools update -f` now reliably restarts the provider

The `FORCE=1` → stop → restart chain was already correct in the script logic, but it only ran if the fixed script was executing. Chicken-and-egg blocked it. With the bootstrap fix above, the new script installs itself before the restart logic runs, so `-f` now reliably stops and restarts the provider.
