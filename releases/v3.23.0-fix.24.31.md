## What's New

### 🐛 Fix — SOCKS5 proxy DNS resolution failure (CPU death spiral)

**Symptom**: On providers behind certain SOCKS5 proxies (including paid proxyscrape endpoints), nearly all proxy auth requests timed out. The provider process spun at 85%+ CPU with 1,750+ proxies stuck in "degraded" state, retrying auth indefinitely, producing 0 billable traffic and 0 earnings.

**Root Cause**: The `golang.org/x/net/proxy` SOCKS5 library sends the target hostname `api.bringyour.com` as-is (FQDN / ATYP=3) in the SOCKS5 CONNECT command, relying on the proxy to resolve it. Some proxies have broken or captive-portal DNS resolvers that return garbage instead of a valid IP, causing TLS handshake failures (`WRONG_VERSION_NUMBER`) or indefinite timeouts on every connection attempt through that proxy. The Go library never attempts local resolution.

**Fix** (PR [#189](https://github.com/full-bars/urnetwork-3.23-fix/pull/189)): In `ProxySettings.NewDialContext` (`net.go`), resolve the target hostname locally via `net.DefaultResolver.LookupIP` before passing it to the SOCKS5 dialer. This converts `api.bringyour.com:443` → `65.49.70.84:443` so the library sends ATYP=1 (IPv4) instead of ATYP=3 (FQDN). Downgrade-safe: if local DNS resolution fails, the original hostname is passed through unchanged.

**Impact**: Eliminates the proxy auth death spiral. Providers that were previously stuck with 100% degraded proxies now authenticate normally, with CPU returning to expected levels as the warmup completes.
