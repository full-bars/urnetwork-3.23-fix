# v3.23.0-fix.26.8 — Proxy Admission Quality Gate, a Dormant Reorder Fix, and CI Summary Repairs

This release adds a second admission gate to URL-source proxy intake: proxies that pass the existing SOCKS5/CONNECT probe are now graded against a sample of the destination table before they're trusted with real traffic, and only the ones that score well enough get admitted. Alongside it, a Linux-only bug that has quietly no-op'd the reorder resilience technique for the fork's entire history gets fixed, and the CI pipeline that watches upstream for portable changes gets three correctness fixes to summaries that were shipping truncated to a single sentence.

## 🗂️ What's New

- **Stage-1 table-probe quality gate for URL-source proxy admission** (#342): proxies surviving the stage-0 handshake probe are now graded against a sampled block of the destination table dialed through the proxy itself, and only proxies scoring above a configurable bar are admitted to the auth queue.
- **TTL fix for the reorder dialer** (#340): the low-TTL value the reorder technique relies on to force retransmits was rejected by Linux and silently discarded, so the technique has been inert in production since the fork began. It's now active.
- **CI: fixed truncated AI summaries in the upstream-monitor pipeline** (#341): a piping bug was keeping 6.6% of every generated summary; three more fixes bound runaway model calls and make the portability verdict aware of what the fork actually shares with upstream.

## ⚠️ Breaking Changes

None. Drop-in upgrade.

## Highlights

> [!IMPORTANT]
> **URL-source proxies now get a second, deeper admission check before they carry traffic** (#342). Previously a URL-source proxy only had to pass stage-0 (a SOCKS5 greeting plus an API `CONNECT`) to be admitted. That's enough to prove the proxy is alive, but not enough to prove it can actually reach the destinations providers need to reach. Stage-1 fixes that: each surviving proxy is dialed at `:443` against a sampled block of the backend's ~127 health hosts (default 12 per pass, 4s per-target timeout), and only proxies scoring `>= pass_bar` (default 0.6, with a 0.9 "preferred" tier) go on to the auth queue.
>
> The design deliberately follows upstream's `ip_remote_multi_client_probe.go`: it only counts positive evidence (a SynAck proves the proxy's own upstream dial actually worked; silence never convicts a proxy, since a target being unreachable for other reasons shouldn't fail the proxy), resolves hostnames through the box's own DNS rather than through the probed channel (so a proxy with broken DNS never fails a TCP probe it should have passed), rotates through disjoint blocks of the sample deterministically, and treats an aborted pass as a decided verdict rather than an unknown one.
>
> A grade only overwrites the previous one when the pass was DECIDABLE — quorum of the requested sample answered, context not cancelled. An empty, cancelled, or resolver-gutted pass leaves the prior grade untouched, which is the same "box's own DNS can never convict a proxy" guarantee applied to the grading loop itself. RFC 1929 auth credentials (`host:port:user:pass`) now carry through both probe stages, so credentialed — usually paid — URL entries are graded on the same footing as free ones instead of failing auth mid-probe. Proxies that grade below the bar never spawn, and the auth gate reports them distinctly from proxies that are simply dead. A kill switch (`~/.urnetwork/proxy_probe.json` with `{"enabled": false}`) restores pre-feature behavior end-to-end, and `sample_width`/`timeout_ms`/`pass_bar`/`preferred_bar`/`enabled` are all runtime-tunable. Score/Graded/Failed now persist in `proxy_url.json` cache entries, matching the backend's own data model.
>
> This went through two rounds of CodeRabbit review plus an independent Opus 5 pass; findings closed include a kill-switch accounting bug, an inert regression test now mutation-verified, a cache-growth bound, and correct handling of credentialed-proxy admission. **Needs a fleet deploy** — this changes provider binary behavior and introduces a new operator-facing config file.

> [!CAUTION]
> **The reorder dialer's TTL manipulation has been inert on every fleet node since the fork's inception, and this release turns it back on** (#340). The reorder technique alternates a connection's socket TTL between 0 and its native value to force retransmits and out-of-order packet arrival at the TLS ClientHello. `IP_TTL` only accepts values 1-255; Linux rejects 0 with `EINVAL`, and `SetSocketTtl` was discarding that error. Every fleet node runs Linux, so the TTL never actually moved, and the reorder and fragment+reorder dialers have been delivering plain fragmentation this whole time while reporting themselves as reorder dialers.
>
> The fix sets the low TTL to 1 instead of 0 — in range, and it still gets dropped at the first L3 hop, which is the loss the technique actually needs — and now returns `SetSocketTtl`'s error so a future out-of-range value fails loudly instead of silently. Two previously-vacuous test assertions are now real; 8 tests were ported from upstream; 34 resilient tests pass, race clean.
>
> This activates a mechanism that has cost nothing on Linux for the fork's whole life, and now costs something real: deliberately dropped segments in the ClientHello flight. Upstream quantifies this at 12 dropped blocks of 24 on the reorder-only path. **Needs a fleet deploy**, and is worth staging on one node before rolling fleet-wide.

> [!NOTE]
> **CI: the upstream-monitor's AI summaries were shipping truncated to one sentence, and three related bugs are fixed alongside it** (#341). Tier-1 summaries were piped through `tail -1`, which kept only the final chunk of the model's streamed JSON output — measured at 6.6% retention (143 of 2153 characters) on a representative run, so every summary that shipped was cut down to whatever fragment happened to be in the last chunk. Three more fixes ride along: the accept guard that was supposed to catch bad summaries couldn't distinguish a real summary from a fragment, so it's now required to be at least 400 characters with a parseable verdict tag (applied at 12 sites); a wedged model call could hang the job for up to 6 hours with nothing timing it out, so all four call sites are now wrapped in `timeout 120`; and the portability rubric was a closed allowlist that had no way to say "the fork shares this code" — `[MUST PORT]` now has to lead with a shared-code citation, and `[NO ACTION]` has to give a positive reason instead of defaulting to it.
>
> Worth being honest about scope here: the truncation, guard, and timeout fixes are deterministic and verifiably correct. The rubric fix is a prompt change, measured at improving one diff's verdict accuracy from 2-of-4 to 5-of-5 correct — a real improvement, but on a single test case, and it's deliberately biased toward false positives (flagging something as portable when it isn't) rather than false negatives. No deploy implications; this only touches the CI monitoring pipeline, not the provider binary.
