## What's New

### API Reachability Probe for URL Proxies

**The problem:** Free public proxy lists are mostly dead. The provider already tested each address with a SOCKS5 handshake before adding it to the pool, but that only checks if something is listening on the port. A surprising number of proxies pass the SOCKS5 check but can't actually route traffic to api.bringyour.com through the tunnel. The proxy itself works, but the path from the proxy to the API is broken (blocked IP range, routing issue, or the proxy is egress-filtering our API).

In production we saw 52 proxies stuck at 51+ retry attempts each, consuming auth-rate-limiter slots and generating "network error reaching API" log lines every 15 minutes indefinitely. The provider's retry logic was working as designed for file-sourced proxies (they never give up), but these were URL-sourced proxies that should have been caught before they ever entered the pool.

**The fix:** We now test API reachability through each proxy during the URL fetch pipeline, before the address is cached, before it reaches the auth rate limiter, before it generates a single log line.

The probe runs in two stages on a single TCP connection per proxy:

1. **SOCKS5 greeting** (3s timeout) -- is this actually a SOCKS5 proxy?
2. **SOCKS5 CONNECT** to api.bringyour.com:443 through the proxy (5s timeout) -- can traffic actually reach the API?

Both stages share one TCP connection, so there's no redundant handshake. The API's IP address is resolved once and cached across all 50 concurrent probes -- no DNS storm. A 100ms random stagger before each probe dial spreads the burst smoothly.

**What happens to each probe result:**

| Result | What it means | What happens |
|--------|---------------|--------------|
| Dead | TCP unreachable, or not a SOCKS5 server | Discarded immediately -- never cached, never logged |
| Socks5-only | SOCKS5 works, but CONNECT to the API failed | Cached, but flagged for background re-probe |
| API-reachable | Both stages passed | Cached as verified, enters auth queue normally |

**Background reaper:** A new goroutine scans the URL cache every 5 minutes for entries that are still unverified (from older versions that didn't track probe state, or from transient failures during the last fetch). Each unverified entry is re-probed. After 3 consecutive failures, the address is added to the persistent blacklist.

**Blacklist pruner:** Blacklisted addresses expire after 24 hours. A pruner runs every 30 minutes and removes expired entries, giving previously-dead proxies a second chance on the next URL fetch cycle.

**The result:** Proxies that can't reach the API are caught at fetch time (within seconds) or within 15 minutes by the reaper, instead of consuming auth slots forever. File-sourced proxies are unaffected by all of this -- they skip the probe entirely, as they should.

### Proxy Summary Command

New `urnet-tools proxy summary` command that shows a single-pane-of-glass fleet overview:

```
=========================================================================
 PROXY SUMMARY
 Updated: 2026-06-27T01:52:43Z
=========================================================================

  Total proxies:      1639
  Up:                 1639
  Connecting:         0
  Degraded:           0
  Dead:               0

 --- Sources ---
  File proxies:       1500  (/home/user/ps1500.txt)
  URL proxies:        139
  Internal proxies:   1

 --- URL Sources ---
  Source URLs:        3
  Cached addresses:   549
  Blacklisted:        0
=========================================================================
```

Reads from on-disk state files -- no provider restart required. Available in both the native binary (`provider proxy summary`) and the `urnet-tools` wrapper, with PowerShell support for Docker deployments.
