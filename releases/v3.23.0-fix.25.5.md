# 🔐 v3.23.0-fix.25.5 — Hub Migration Race Fix

> **TL;DR** Small point release on top of v3.23.0-fix.25.4: fixes a real (if rare) race condition in the hub's `proxy_fleet_hourly` backfill migration, and reorganizes `urnet-tools`' help text so hub commands have their own section. No provider behavior changes. No breaking changes — drop-in upgrade.

This release exists mainly to get a hub binary release out with the migration race fix below — `urnet-tools hub update`/`hub install` only pull hub binaries from provider `v*` tag releases, not from the hub's own `hub-v*` Docker image tags, so a provider point release was the fastest way to make the fix available through the normal update path.

---

## 🐛 Hub Migration Race Fix

> **The bug:** The `proxy_fleet_hourly` backfill migration (added in v3.23.0-fix.25.4 alongside the Best Proxies leaderboard) spawns an async goroutine to backfill historical data on upgrade. It was gated only on the *destination* table (`proxy_fleet_hourly`) being empty — which is true for every brand-new store, not just real upgrades. That meant the goroutine fired unconditionally on every fresh store, racing against whatever ran next against the same tables. This surfaced as intermittent duplicate-row test failures under `-race` while porting this migration to another codebase — the bug was real, just hadn't been triggered yet in this repo's own test runs.

**The fix:** Gate on whether `proxy_node_hourly` actually has rows old enough to backfill, not just on the destination being empty. A fresh store has nothing to backfill either way, so this also means the goroutine no longer spawns at all on fresh installs — not just in tests.

**Verified:** `go test -race -count=15` clean in both this repo and the port target.

## 🐛 urnet-tools: Hub Commands Get Their Own Section

The `hub set/test/open-port/show-password/onboard-cmd/off/install` commands were listed under "Proxy Management" in `urnet-tools`' help text, which had nothing to do with the hub. They now have their own "Hub:" section.
