## What's New

### 🐛 Fix — 100% CPU spin from self-wake feedback loop in transport mode monitor

**Symptom**: Since v3.23.0-fix.24.27 (June 30), providers consume 100%+ CPU even with **zero proxies and zero clients**. The Go scheduler shows both P-threads never idle (`idleprocs=0`), cycling ~16,000 goroutine events per second. Strace reveals 8,000 futex + 4,600 nanosleep calls per second — ~1000× normal for an idle process. Affects all deployments, independent of proxy count.

**Root Cause**: Commit 1f64686 (PR #188 — live heartbeat SSE push) added `modeMonitor.NotifyAll()` to `setActiveMode()` so mode-waiting goroutines would be woken immediately on changes. However, `PlatformTransport.run()` calls `setActiveMode(mode)` on **every** loop iteration unconditionally — even when the selected mode is already active. `NotifyAll()` closes the notify channel that `run()` literally just captured half a loop iteration earlier via `modesAvailable()`. The `select { case <-notify: }` fires instantly. The loop body (which clones the mode map, extracts and sorts all keys) executes ~8,000 times per second per P-thread, forever.

Each `NotifyAll` also wakes 4+ other mode-waiting goroutines (H1/H3 read/write loops), which check the mode, find nothing changed, and re-park — creating the futex storm and saturating the second core.

**Fix** (PR [#191](https://github.com/full-bars/urnetwork-3.23-fix/pull/191)): Gate `NotifyAll()` on actual state change — only fire the wake signal when the mode or availability genuinely transitions. `run()` now blocks normally on its select, waiting for real mode changes from `setModeAvailable` or external triggers. Same guard applied to `setModeAvailable()`.

**Affected releases**: v3.23.0-fix.24.27 through .32. First shipped June 30, 2026.
