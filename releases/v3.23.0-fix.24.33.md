## What's New

### 🐛 Fix — 100% CPU self-wake feedback loop in platform transport

**Symptom**: Since v3.23.0-fix.24.27 (June 30), providers consume 100%+ CPU at all times — even with **zero proxies loaded and zero client traffic**. The process saturates both available CPU cores indefinitely, from the moment the platform WebSocket connects until the process is killed. The CPU burn produces no logs, no errors, and no visible symptoms other than the utilization itself.

**Root Cause**: Commit `1f64686` (part of the live heartbeat SSE push in [#188](https://github.com/full-bars/urnetwork-3.23-fix/pull/188)) added a notification to `PlatformTransport.setActiveMode()` so that goroutines waiting on transport mode changes would be woken immediately. However, the transport's `run()` loop calls `setActiveMode()` on every iteration — even when the mode hasn't changed. Each call closes the notification channel that `run()` *literally just captured on the previous line*, causing the `select` at the bottom of the loop to fire instantly.

The result is a self-wake feedback loop: `run()` checks available modes, picks one, fires the notification, the notification wakes `run()` back up, and it does it all again. Forever. The loop body is not trivial — it clones the mode map, extracts and sorts all keys — and runs ~8,000 times per second per CPU core. Each notification also wakes several other worker goroutines which check the mode, find nothing changed, and go back to sleep, doubling the churn.

**Fix** (PR [#191](https://github.com/full-bars/urnetwork-3.23-fix/pull/191)): The notification is now gated on actual state change — `NotifyAll()` only fires when the mode or availability genuinely transitions. `run()` blocks normally on its select, waking only when a real mode change occurs. The same guard is applied to `setModeAvailable()`.

**Affected releases**: v3.23.0-fix.24.27 through .32. First shipped June 30, 2026.

**What this means for operators**: If your provider has been consuming 100%+ CPU since late June with no corresponding traffic increase, this release should eliminate that overhead. The fix is safe — it only removes unnecessary wake-ups; mode-change notifications still fire exactly when they should.
