# v3.23.0-fix.30.6 — 2026-08-22

> [!NOTE]
> Operators should update the Go tools (`urnet-tools`, `urnet-docker`) to pick up in-place container updates that now work on any image, and to get real per-command help across every command. Go 1.27 is required to build this release. This release is CLI, tooling, and observability focused. The provider network stack itself is unchanged.

## 1. Summary

This release closes out the in-place container update work started in v3.23.0-fix.30.5, finishes the Cobra help migration, and adds post-quantum session visibility to the provider. `urnet-docker update` now repairs an older container's broken update script from the host first, then swaps the binary in place and auto-restarts the same container if the swap stops it. It also accepts a bare container name, matching the other docker commands. Every `urnet-tools` and `urnet-docker` command now renders a genuine per-command help page with a description and copy-paste examples. The provider detects whether an end-to-end session negotiated a post-quantum or classical key exchange and reports it in the logs and a new periodic summary line. This is all one PR, #455.

## 2. In-Place Container Update on Any Image

- **Host-side repair before update (PR #455)**: `urnet-docker update` previously delegated entirely to the container's own update script. Older images ship that script broken: busybox `mktemp` rejects the `XXXXXX.tar.gz` template, and `pkill -x` misses the process name once it is truncated to 15 characters. In-place update failed on old-image containers with `mktemp: Invalid argument`.
- Now the command repairs the container's update script from the host first. The repair is idempotent, so running update repeatedly does not re-patch an already-fixed container.
- After the repair, the command swaps the provider binary in place. If the swap stops the container, which older images do instead of relaunching cleanly, the command auto-restarts the same container. The container ID does not change and there is no recreate.
- `urnet-docker update <name>` now also accepts a bare container name, matching the targeting convention used by the other docker commands.
- Verified live on a real container running an older 26.4 image: the binary was swapped to the new version in place, the container ID stayed the same, and the provider came back up on the new version.

> [!NOTE]
> This closes the known limitation called out in v3.23.0-fix.30.5, where a container built from an image predating the update-routine fix had to be recreated from a current image to update.

## 3. Real Per-Command Help

- Every `urnet-tools` and `urnet-docker` command's `-h`/`--help` now renders a genuine per-command page with a clear description and copy-paste examples, finishing the benefit of the Cobra migration landed in v3.23.0-fix.30.5.
- `urnet-docker proxy` is a real parent command with 12 per-subcommand help pages.
- `exec -h` shows exec's own help. Help text supplied after `--` is still forwarded to the container command, so in-container help is unaffected.

## 4. PQE Session Visibility

- The provider now detects whether a per-peer end-to-end session negotiated a post-quantum key exchange, one of `X25519MLKEM768`, `SecP256r1MLKEM768`, or `SecP384r1MLKEM1024`, versus a classical curve. Detection reads the negotiated curve from the TLS connection state (`tls.ConnectionState().CurveID`), which requires Go 1.27.
- Session-up and session-close log lines are tagged `[pqe-<curve>]` for post-quantum sessions and `classical` otherwise.
- A rolling tracker counts session-opens live and over 1h, 24h, 7d, and lifetime windows, split between PQE and classical.
- A periodic `[pqe]` provider log line reports live and windowed PQE and classical counts.
- The tracking logic was reviewed and corrected before merge: each session is counted once on open, the PQE-vs-classical classification is persisted for the life of the session rather than re-derived, and only the promoted epoch reports counts, so a synthetic or superseded epoch cannot double-report.
