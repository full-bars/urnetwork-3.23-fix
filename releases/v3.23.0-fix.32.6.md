# v3.23.0-fix.32.6

> [!NOTE]
> This release fixes credential flip-flopping on paid proxies that share a gateway address. When two accounts pointed at one host:port, the provider treated them as one proxy, so which account was "running" changed on every reload and the proxy rotated in a loop. Proxy identity is now the address plus the username, everywhere the provider tracks a proxy. Nodes running credentialed proxies that share a gateway should update.

This is a focused fix release. Its one fix changes how the provider identifies a proxy, and a second change carries the saved client logins across to the new identity.

## What's Changed

### Fixed

- **Two accounts at one gateway address collapsed into one proxy** ([#684](https://github.com/full-bars/urnetwork-3.23-fix/pull/684)): the provider keyed its proxy state, health registry, earnings history, grading, audit, trim, removal and refresh logic by bare address. Two accounts behind the same gateway therefore shared a single entry, and which account won flipped on each reload, so the proxy rotated its credentials in a loop. A proxy is now identified by `ProxySettings.Key()`, the address plus the username (the password is not part of the identity, so a genuine password change is still a rotation of the same proxy). Existing proxy state and earnings history migrate to the new keys on start; unauthenticated proxies keep their address as their identity, so they see no change. The change went through four review rounds, each of which found remaining places that still passed a bare address to an identity-keyed lookup, and all of those are fixed with regression tests.
- **Saved client logins keyed by identity too** ([#685](https://github.com/full-bars/urnetwork-3.23-fix/pull/685)): the hot-restart login store was still keyed by bare address, so two accounts at a shared gateway shared one saved login and one account's revocation eviction deleted the other's. It is now keyed by proxy identity, and existing entries are adopted onto the new keys on start and on reload.

- **Startup no longer stalls on a large saved-login store** ([#687](https://github.com/full-bars/urnetwork-3.23-fix/pull/687)): adopting saved logins onto the new identity keys rewrote the whole login store once per login. On a node with thousands of saved logins that held every proxy back for minutes to hours after a restart. Adoption now moves every login with a single write, and a node with a large store starts its proxies in seconds.

### Maintenance

- **Flaky reload test** ([#686](https://github.com/full-bars/urnetwork-3.23-fix/pull/686)): a rotation test never reserved proxy ID 0 for `[direct]` the way production does, so it failed intermittently when run on its own. Test-only, no provider behavior change.

## Deploy Notes

1. **Update and restart, no config changes.** `urnet-tools update` picks up the fix. Proxy state, earnings history and saved logins migrate automatically on the first start.
2. **Most affected: nodes running credentialed (paid) proxies where more than one account shares a gateway address.** Nodes whose proxies each have their own address see no behavior change.
3. **One extra fresh login for some accounts, once.** When several accounts share an address, exactly one of them (the lexicographically smallest key) inherits the existing saved login. The others mint a fresh login on their next start. Every other proxy keeps its saved login, so hot-restart reuse is unaffected.
4. **The migration is one way.** Rolling back to a build older than this one makes the affected proxies mint fresh logins once, because the old build looks them up by bare address. Re-running this build is safe: the migration is idempotent.
