# v3.23.0-fix.32.2

> [!NOTE]
> **First update after this release:** the audit ring loads on the new process and the old process flushes before it hands over, so `urnet-tools history` shows the update itself. On a node updated with `urnet-tools update -f`, you will see a `hotswap` entry followed by a `start` entry with the new version.

This release is all about making the provider's audit trail survive an update. I also tightened the status line so it stops crying wolf on a healthy node.

## What's Changed

### Added

- **Audit ring now records lifecycle events** ([#668](https://github.com/full-bars/urnetwork-3.23-fix/pull/668)): `urnet-tools history` used to show only `set` and `clear` config changes. It now also records process start (with the version), the hotswap handoff, and control-socket shutdown. After an update you see the story: `hotswap` on the old process, then `start` with the new version on the successor.

- **Audit entries survive hotswap** ([#668](https://github.com/full-bars/urnetwork-3.23-fix/pull/668)): the old process flushed its audit ring at the handover point, before the takeover message, on every path (systemd, Windows, Docker). The new process then merges the ring from disk and deduplicates it, so the last commands you issued before an update are not lost. The old process also closes its control socket at that same point, so nothing accepted after the flush can disappear in its memory.

### Changed

- **Provider status uses a sliding severity scale** ([#668](https://github.com/full-bars/urnetwork-3.23-fix/pull/668)): the systemd status line now reads `active` when 90% or more of the configured proxies are live, `partial` between 70% and 89%, `degraded` between 50% and 69%, and `critical` below 50% (including zero). The exact percentage always shows: `active: 1313/1367 proxies authenticated (96%)`. A node with a normal dead tail of proxies no longer reads as "partial" forever, and the percentage is clamped at 100 so a mid-reload count never renders nonsense.

- **Start entries persist immediately on normal boots** ([#668](https://github.com/full-bars/urnetwork-3.23-fix/pull/668)): only a hotswap successor holds its start entry in memory until the takeover merge. A regular boot keeps writing immediately, so a crash within thirty seconds cannot lose your start record.

## Deploy Notes

1. **No unit changes.** This is a provider runtime change only; existing installs pick it up on the next `urnet-tools update -f`.
2. **`urnet-tools history` shows more.** Lifecycle entries are new; paging and the 1000-entry ring are unchanged.
