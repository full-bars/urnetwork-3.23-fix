# v3.23.0-fix.35.1

**Released:** 2026-10-24. **Previous release:** `v3.23.0-fix.35.0`.

This covers everything merged since `v3.23.0-fix.35.0` (PRs 979 to 994). The one-line-per-change list is the Unreleased section of [CHANGELOG.md](../CHANGELOG.md).

This window is mostly reliability and installer work on top of the extender release. The largest operator-visible change is the proxied H3 outage-egress fix: a node on `h3 all`, a count or `auto` stops spending a flat stream of failed QUIC dials when the platform edge goes silent. Alongside it the degraded reaper no longer culls half the pool on a tie, a planned thrash restart is no longer logged as a rejected sign-in, a FreeBSD installer exists, and the installer hardening for it is in.

Legend: **[redeploy]** needs the built artifact redeployed. **[installer]** needs the installer or unit refresh. **[no redeploy]** docs, CI or tests only.

## Transport

- **A silent platform edge no longer drains egress through proxied H3** **[redeploy]** (<https://github.com/full-bars/urnetwork-3.23-fix/pull/994>). With `h3` set to `all`, a count or `auto`, every proxy identity runs the H3, H3-over-dns and dns-pump carriers beside its H1. When the edge answers nothing, each carrier redials on its own 30 to 60 second timer and every dial runs the whole QUIC retransmit ladder, about 33 KB. One node on `h3 all` spent a flat 15.5 to 16.4 Mbit/s for about 15 hours of the 2026-10-23 outage, roughly 30 times more tx than rx, while the governor read `verdict=ok rate=200.0/s`. Three things hid it, and each is fixed: QUIC bytes were never charged to the connect attempt, so the failed-byte breaker saw zero; a canceled dial (two of every three, because the per-transport H3 gate cancels a lower-priority carrier when a better one waits) was dropped with its bytes; and H3 dials never waited on the attempt budget. The handshake's wire bytes are now charged once, a canceled attempt's bytes count toward the breaker without counting as an attempt, and a proxied identity's H3 waits on the shared budget like its H1. The direct identity, proxy index 0 and family-pinned transports never wait.

## Provider

- **A failed OOM-cap state write is reported, not discarded** **[redeploy]** (<https://github.com/full-bars/urnetwork-3.23-fix/pull/993>). The startup OOM-cap decision wrote its state with the result discarded. That state carries the cap and the clean-window clock, so a lost write could let the next start read a stale window and relax the cap straight after a fresh OOM kill, and the applied path could ledger a cap that nothing enforces. Both branches now report the failure in the warnings, and the applied path leaves the timeline to the last cap that really was persisted.
- **The memory-headroom warning fires at the cap on a host whose RAM is unreadable** **[redeploy]** (<https://github.com/full-bars/urnetwork-3.23-fix/pull/990>). `EffectiveRAMLimit()` returns 850 MiB with the source `fallback default, host memory unreadable` when it cannot read host memory, which the headroom threshold turned into its 150 MiB floor, so the warning fired far too late on such a host. The limit is now classified by its source, never its value: an unreadable host gets the 400 MiB cap, a real 850 MiB host keeps the floor, and the note explaining the threshold goes to the persisted log once.
- **The degraded reaper holds off when the scores cannot rank the pool** **[redeploy]** (<https://github.com/full-bars/urnetwork-3.23-fix/pull/986>). `scoreDegradedProxies` ranks by lifetime bytes and contracts, and when the platform is unreachable neither moves, so every candidate tied and the reaper still dropped half the pool (249 of 498 proxies on one node in the 2026-10-23 outage). A round where every candidate scored the same, or there are too few to rank, now holds off instead of culling.
- **The smart dialer costs nothing while it is off** **[redeploy]** (<https://github.com/full-bars/urnetwork-3.23-fix/pull/989>). The idle preference's off state still cost a goroutine, a context and a timer per proxy, so a node with thousands of proxies carried thousands of idle goroutines. The start function is gated, so while the preference is off there is none. Because the loop now only exists when the preference was on at start, `smart_dialer` is reclassified restart-required: `set smart_dialer on` is persisted and takes effect at the next start, the CLI says so, and `set` now prints the same "takes effect at the next start" wording for `profile` and `ramlogs`, which never applied live. The default is unchanged: off.
- **A planned thrash restart is no longer logged as a rejected sign-in** **[redeploy]** (<https://github.com/full-bars/urnetwork-3.23-fix/pull/988>). Exit code 75 has two producers: a failed sign-in quarantines the child, and the thrash watchdog's planned restart also exits 75. The supervisor only knew the first, so a thrash restart was reported to the operator as a rejected network sign-in. Every planned exit 75 (the thrash watchdog and the liveness self-exit) now writes a one-shot `thrash_exit.<pid>` marker beside `thrash_cap.json` immediately before it exits, and the supervisor consumes the marker for the pid it reaped. A first approach compared the mtime of `thrash_cap.json` with the child's start time and was dropped, because that file is also written mid-life and a later genuine quarantine would have been misread. Only the operator log line changes: both branches make the same state changes, the automatic sign-in backoff comes from the set-aside files on disk, and the exit code stays 75, so the systemd units, container start scripts and OpenRC keep restarting on it. `docs/Troubleshooting.md` now lists both meanings.
- **A hotkey wallet write no longer fails on Windows** **[redeploy]** (<https://github.com/full-bars/urnetwork-3.23-fix/pull/985>). After the rename the write flushed the parent directory. Windows can open a directory handle but has no directory flush: `FlushFileBuffers` answers access denied, so the write was reported failed even though the file was in place, for both the originals chain and the pending statement. The flush now goes through `internal/durablesync`, which keeps the directory precondition and absorbs only the errnos that mean the platform has no directory flush. Every other failure still reaches the caller, and on Unix it is the same fsync as before. The pre-fix code was seen failing on a Windows host (`sync ...hotkey-wallet: Access is denied`) and a write completes and reloads with the change; the Windows job now runs the helper's tests.
- **Five extender review findings are acted on** **[redeploy]** (<https://github.com/full-bars/urnetwork-3.23-fix/pull/980>). These were review findings on the extender stack that were not acted on before the 35.0 release. The feed read deadline is set before the cancellation hook is registered, and a started cancel hook is awaited before the stream is reused, so a canceled or late hook cannot arm an immediate deadline on a later read. A zero connect timeout stays unbounded on the http3 carrier, matching the tcp carrier, and an unbounded connect aborts when the context ends. Issued-key pruning walks the table only when the epoch changes, not on both reads per request. Service and refusal counts of retired servers are sampled after the server has drained and folded into the base counters once, so metrics declared cumulative keep their totals. VLESS response-header parsing keeps the bytes already consumed, completes the header before reporting a read error, and can resume after a read timeout once the caller refreshes the deadline. The extender is opt-in and off by default, so this matters only on nodes serving the role.

## Observability

- **The disk benchmark samples by time, not a fixed 16 MiB** **[redeploy]** (<https://github.com/full-bars/urnetwork-3.23-fix/pull/992>). The benchmark stopped at a fixed 16 MiB, which an NVMe writes in about 20 ms, so the rate reported at startup and in `urnet_disk_*` was a burst figure that moved between runs. The 3 s budget now governs, up to 256 MiB: microSD is unchanged at about 20 MiB, eMMC samples about 240 MiB, NVMe the 256 MiB ceiling in about 85 ms. The result carries its duration, so the log reads `900.0 MB/s (256 MB written in 85 ms)`. The container guard, IO-pressure skip, space cap, per-device cache and hung-write watchdog are unchanged.
- **`psi_some_avg60` now appears in the baseline host sample** **[redeploy]** (<https://github.com/full-bars/urnetwork-3.23-fix/pull/983>). The memory pressure figure lives inside `/proc/pressure/memory`, but the reader asked for a resource named after the line (`some`), which does not exist, so the read errored and the omission rule dropped the field from every sample on every node. The call now asks for the memory resource, and a package-level seam pins the resource name so a rename cannot reintroduce a path that does not exist. The same defect was found and fixed in `sn`.

## Install and CI

- **A FreeBSD provider installer** **[installer]** (<https://github.com/full-bars/urnetwork-3.23-fix/pull/979>). `docs/FreeBSD.md` told FreeBSD users to fetch `scripts/Provider_Install_FreeBSD.sh` from `main`, and that file did not exist, so the documented command returned a 404 while Linux, macOS and Windows all had an installer. The script now exists, adapted to this repo: repo references point at `full-bars/urnetwork-3.23-fix`, the provider asset is the per-architecture FreeBSD tarball the release publishes (`urnetwork-provider-<tag>-freebsd-<arch>.tar.gz`), and `urnet-tools` comes from the same release. The tag resolves through the GitHub API and falls back to this fork's mirror, the same pattern the other installers use. Provider files go to a system-wide location while service state stays in the service user's home, the service user can be overridden explicitly, installed files get restricted ownership and permissions, and the service refuses to start if its output log is a symbolic link. It was checked against the live 35.0 release assets and `sh -n`; a full install on a FreeBSD host is not recorded in the PR.
- **The installer refuses a symlinked service path and an unusable binary, and no longer needs python3** **[installer]** (<https://github.com/full-bars/urnetwork-3.23-fix/pull/984>). `mkdir -p` follows a link and the `chmod` has no `-h`, so a symlinked home or state directory sent root somewhere else. The guard covers both and a symlinked parent, and runs first in `do_install`, before the download, so a refusal cannot leave a half-done install. A binary that is not a non-empty executable is refused before it replaces a working one, where a truncated download used to produce a provider that failed at exec time after the old binary was already renamed away. The release tag is read with `jq`, then `python3`, then a `sed` extraction, because python3 is not in the FreeBSD base system and a default latest install failed on a clean host and blamed the GitHub API.
- **The FreeBSD installer no longer follows a symlinked shell rc** **[installer]** (<https://github.com/full-bars/urnetwork-3.23-fix/pull/987>). The installer runs as root, appends a PATH line to the service user's rc file and changes its owner, and both operations followed a symlink, so a link planted at `.profile` sent root's append and ownership change to a file of the user's choosing. A symlinked rc is now refused with a warning and the install carries on, since the provider is already in place. For a real file the new content is built in a `mktemp` file beside it, owned, given the original mode and renamed over the target, so the rename replaces the directory entry instead of following it. The PATH line appears once across repeated runs. The test requires the unfixed version from `origin/main` to still write through the link, so it cannot pass vacuously. The same block is carried in the sibling repos and was fixed alike there.
- **FreeBSD is served from the universal autoinstaller** **[no redeploy]** (<https://github.com/full-bars/urnetwork-3.23-fix/pull/981>). The universal autoinstaller sent any `uname` it did not recognise to Unsupported OS, which included FreeBSD. The `dl` worker now routes FreeBSD to `install-freebsd.sh`, with the matching wrangler route and alias, and its landing text names Linux, macOS and FreeBSD and says the Linux path covers OpenRC. The FreeBSD installer script it points at is the one added above. This is the `dl` worker, so it deploys separately from the provider.
- **The installer PATH-hint test runs in CI** **[no redeploy]** (<https://github.com/full-bars/urnetwork-3.23-fix/pull/991>). `scripts/test_provider_install_shellrc_symlink.sh` proves the installer's PATH hint never writes through a name the service user controls, and it never ran in CI. It now runs with full history, and the script fails, not skips, when its falsification pin is missing under `REQUIRE_FALSIFICATION`, so a shallow checkout cannot turn it into a silent pass.
- **The extender relay counter test bounds read counts** **[no redeploy]** (<https://github.com/full-bars/urnetwork-3.23-fix/pull/982>). The test pinned one read per write, but how the transport splits a write into reads is not something the relay controls: the same session reported four ingress reads on one run and three on another. Byte counts stay exact and read counts are bounded between one per chunk and one per byte, so the test still proves every relayed read is counted without failing on segmentation. It fixes a shard 2 flake.

## Deploy notes

- **`smart_dialer` is now restart-required.** A node that runs `urnet-tools set smart_dialer on` sees the change at its next start, not live, and the CLI says so. The default is still off.
- **Only nodes with `h3` set to `all`, a count or `auto` change for the H3 fix.** Nodes on the default `h3 direct` dial H3 from the direct identity alone and spent 0.1 to 1.1 Mbit/s in the same outage. `urnet-tools set h3` shows the setting. In an outage those nodes log `[govern] budget cut ... reason=bytes`, which was silent before.
- **The disk figure changes on fast media.** The first benchmark after the update samples up to 256 MiB, so an NVMe rate is a representative figure and no longer a 20 ms burst that moved between runs. Slow media report what they did before.
- **The provider needs a redeploy** for the provider changes above. There is no unit change and no new required setting.
- **The `dl` worker deploys separately** (`workers/dl`) for the FreeBSD route. The FreeBSD installer script it points at is already on `main`.

## Caveats

- The H3 fix has not been run against a live outage. The attempt budget floor is 2 per second, so a throttled node still spends about 0.5 Mbit/s, not zero. A silent timeout still carries no weight in the governor's verdict, on purpose: a proxy that cannot relay UDP fails the same way whatever the backend does.
- The FreeBSD installer and its hardening were verified with harnesses and `sh -n`, not by a recorded end-to-end install on a FreeBSD host.
- The extender fixes are covered by unit tests; the extender role has still not been proven at fleet scale.
