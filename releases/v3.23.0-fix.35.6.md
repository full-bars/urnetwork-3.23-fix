# v3.23.0-fix.35.6

**Released:** 2026-11-08.

Previous release: [v3.23.0-fix.35.5](https://github.com/full-bars/urnetwork-3.23-fix/releases/tag/v3.23.0-fix.35.5).

I fixed a RAM log that could go silent during a HotSwap. I also fixed an update check that could report a successful handoff as unconfirmed, made the installer write a `Type=notify` unit by default, and made the updater and installer report unsafe or incomplete steps more clearly.

Legend: **[redeploy]** needs the new provider, tool or container image. **[installer]** needs the updated installer or script. **[no redeploy]** covers documentation, CI and tests.

## Quick start

Install on Linux or macOS:

```sh
curl -fSsL https://install.fullbars.xyz | sh -s -- install
```

On FreeBSD, run the installer as a non-root service account with sudo:

```sh
fetch -qo - https://install.fullbars.xyz | sudo sh -s -- install
```

On Windows, use PowerShell:

```powershell
irm https://dl.fullbars.xyz/install-win.ps1 | iex
```

Run the provider in Docker with a persistent volume and a single-use auth code from https://ur.io:

```sh
docker run -d --name urfix --pull always --restart unless-stopped --cap-add NET_ADMIN --cap-add NET_RAW --sysctl net.ipv4.ip_forward=1 -e AUTH=authcode -e AUTHCODE='YOUR_AUTH_CODE_HERE' -v urnetwork_data:/root/.urnetwork ghcr.io/full-bars/urnetwork-3.23-fix:latest
```

This release is the provider line. For miner setup, use the separate miner release and its instructions; this workflow does not publish a miner image.

## What changed

### Provider and updater [redeploy]

- The Linux RAM log follows its path when another process replaces it or the file is removed. The important log in the state directory is also checked. Reopens reject symlinks, unsafe file types, ownership and permissions. A rate-limited notice reports a successful reopen.
- When the running image cannot be read, the updater can verify the new version through the provider control socket. On Linux it checks the listener's kernel credentials against the discovered new process before accepting the reply. The version must match the release.
- A failed verification now reports what the updater observed instead of asserting that a handoff failed. If it cannot safely reconcile the systemd unit and the installed binary, it stops before restarting and gives repair instructions. A failed rollback names the backup and says the provider was not restarted.
- On Linux, the updater tries to restore the extender port capability only when it verified that the old binary had it. A non-root caller uses non-interactive sudo. If restoration is not possible or the old capability was not verified, the tool prints a command to run.

### Installer [installer]

- The Linux installer explains the extender and its ports in plain words. When needed, it offers to grant port 443 permission only on an interactive terminal. Piped or redirected input or output skips the offer and prints the command instead.
- Systemd setup failures report which steps completed and print a recovery command. Rollback reload and start failures are also reported.
- The installer now writes `Type=notify` and `NotifyAccess=all` in the provider unit it generates, because HotSwap needs both. An older `Type=simple` unit is still migrated by `urnet-tools update`. **[installer]** A new install or reinstall applies this; an existing node changes on its next update.
- Login linger, OpenRC ownership, immediate and persistent sysctl, firewall detection and downloaded tool install now print what failed and the exact command to run. Before, they could stay silent.

### Documentation [no redeploy]

- The release notes, changelog, fork notes and guides describe these changes and their limits.

## Known limits

- Some installer steps still hide errors: the legacy shell tool fallback, OpenRC state and log setup, capability setup and ZRAM tuning. The optimizer still prints a success line when a step failed. I plan to fix these in the next release, with non-interactive approval for restart and optimize and the OpenRC sudo-path failure handling.
- The log change has deterministic tests and a child-process trim test; it has not been verified in a full two-process HotSwap on a host.
- When updating from a version without this log fix, the outgoing process still runs the old log code.
