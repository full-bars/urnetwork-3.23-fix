## Turbo mode + Watchtower JWT persistence

### Turbo mode V4 / V8 (new in fix.13)

The provider's per-connection throughput is bounded by TCP window size divided by round-trip time. At the 1 MiB default window and a 10ms RTT, that's ~100 Mbps — not a hard limit in the code, just physics. On RAM-rich servers with fast upstream links, this means the provider never reaches full potential even with a large proxy list.

Turbo mode raises the window ceiling:

| Profile | Window | Theoretical ceiling @ 10ms RTT | RAM requirement |
|:---|:---|:---|:---|
| **Turbo V8** | 8 MiB | ~800 Mbps | 16 GiB+ |
| **Turbo V4** | 4 MiB | ~400 Mbps | 4–16 GiB |
| *(default)* | 1 MiB | ~100 Mbps | 2–4 GiB |

A larger window is only useful if the supporting structures can fill it. The following scale with the window to prevent them becoming the new bottleneck:

- **Resend and receive queues** (SendBufferSettings / ReceiveBufferSettings): raised to 2× the window (8 MiB for V4, 16 MiB for V8). Without this, sends stall waiting for acks once the queue fills, which collapses throughput regardless of window size.
- **IP-layer sequence buffer depth**: 256 → 512. Prevents packet reordering drops at higher throughput.
- **Transfer-layer sequence buffer depth**: 16 → 64. Same reason at the transfer layer.
- **WebRTC DataChannel receive buffer**: set to 2× window per peer so P2P paths scale along with TCP paths.
- **Contract ramp acceleration**: `ContractTransferByteSeqScale` 4 → 2, so full contract speed is reached in 2 contracts instead of 4. This eliminates the slow ramp period at connection start.
- **GC tuning**: GOGC raised to 200 with no GOMEMLIMIT. On RAM-rich boxes the default GC pressure is counterproductive; letting the heap breathe reduces CPU overhead during high-throughput transfers.

**To enable:**

Docker — single env var:
```bash
-e TURBO=v4   # or v8
```

Linux service — new urnet-tools commands:
```bash
urnet-tools turbo v4     # enable Turbo V4
urnet-tools turbo v8     # enable Turbo V8
urnet-tools turbo off    # back to defaults
urnet-tools turbo        # show current state
```

### Watchtower / JWT persistence fix (new in fix.13)

Providers running in Docker with auto-update tools (Watchtower, `--restart=unless-stopped`, host reboots) were losing authentication on every container recreation. The startup script was deleting the JWT on each boot, forcing re-authentication — which consumes a single-use auth code. On a fleet with many containers, Watchtower pushing an update at 3am would exhaust auth codes and put all containers into a panic loop.

Two root causes addressed:

1. **Startup script no longer deletes the JWT.** It now checks for an existing JWT at `/root/.urnetwork/jwt` and skips authentication entirely if one is found. The provider starts immediately without touching the API. Auth codes are only consumed on first run or after a manual JWT clear.

2. **Provider binary no longer panics on auth failure.** Auth errors (expired JWT, revoked code, API rejection) now print a clean message to stderr and exit with code 1, letting the shell restart loop handle recovery. After 10 consecutive API rejections the binary exits so the restart loop can clear the bad JWT and trigger a fresh login — previously the binary looped forever internally, making recovery impossible without manual `docker exec`.

**Required:** mount a named volume at `/root/.urnetwork` so the JWT survives container recreation:

```bash
-v urnetwork_config:/root/.urnetwork
```

Without this volume, any container recreation wipes the JWT regardless of this fix. Each instance should get its own named volume if running multiple containers.

### Other fixes

- Crash loop in `start_stable.sh` now calls `func_do_login` (not `func_check_credentials`) after clearing a bad JWT — previously the recovery path re-checked credentials rather than actually re-authenticating
- Auto-update timer now starts immediately on install/reinstall. The install script was using `systemctl --user enable` instead of `enable --now`, so on servers that hadn't rebooted since install the timer was registered but never started
- `urnet-tools logs` now correctly routes to `/dev/shm` when eco mode is active (was only checking for lowmem, leaving eco users tailing journald instead of the RAM log)
