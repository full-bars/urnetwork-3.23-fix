# v3.23.0-fix.25.3 — Hub CA Trust System & Proxy Reload Fixes

The major feature this release is a **password-derived Certificate Authority** for hub↔provider TLS trust, replacing the old TOFU fingerprint-pinning (`hub.pin`) with real X.509 chain verification. Also includes a critical fix for the proxy hot-reload mechanism that was causing infinite reload loops on providers with many URL-sourced proxies.

---

## Hub CA Trust System

### Deterministic TLS Trust

The hub now derives an Ed25519 CA from an operator-chosen password using Argon2id (memory-hard KDF). The same password + salt always produces the byte-identical CA certificate — surviving hub restarts and data dir loss without re-pinning providers.

- **`hub/ca.go`**: `deriveCA`, `issueLeaf`, `leafSANs`, `loadOrCreateCAMaterial`
- **Ed25519 CA key** — deterministic, stable across Go toolchain versions
- **ECDSA P-256 leaf cert** — rotating, ephemeral, 48h validity, reissued every 24h
- **Argon2id** — time=3, memory=64MiB, threads=4

**On-disk format:**

| File | Purpose |
|---|---|
| `hub.password` | Operator password (plaintext, 0600) |
| `hub.salt` | 32 random bytes, never leaves the hub |
| `ca.crt` | Public CA cert, written each startup |

### Provider Verification (Fail-Closed)

The provider's report client now prefers CA verification over legacy fingerprint pinning. When no trust material exists at all, the provider **fails closed** with a clear error instead of silently accepting any certificate (closing the MITM window that existed in bare TOFU).

Decision ladder:

1. Non‑https URL → plain HTTP client (unchanged)
2. `~/.urnetwork/hub_ca.pem` exists → real X.509 chain verification
3. `~/.urnetwork/hub.pin` non‑empty → legacy strict pin + deprecation warning
4. Otherwise → fail closed with actionable error

### Token-Based Onboarding

New friction‑free provider onboarding — mint a 15‑minute join token, paste one curl one‑liner into each provider, done. No SSH, no file copy, no `urnet‑tools` dependency on the provider node.

```sh
# On the hub:
urnet-tools hub onboard-cmd

# On each provider:
curl -fsSL http://HUB_IP:8080/onboard.sh | sh -s -- TOKEN
```

- Token is reusable across the entire fleet for 15 minutes
- Token persists to disk across hub restarts
- One `onboard-cmd` run mints one token; multiple runs coexist independently

### Operator CLI

| Command | What it does |
|---|---|
| `urnet-tools hub init --password "pw"` | Set a password and enable TLS on :8443 |
| `urnet-tools hub init` | Auto‑generate password, enable TLS |
| `urnet-tools hub show-password` | Print the hub's current password |
| `urnet-tools hub onboard-cmd` | Mint token, print curl one-liner |
| `urnet-tools hub link <url> [--token <t>]` | Fetch CA cert via token or manual TOFU |
| `urnet-tools hub test <url>` | CA chain verification (preferred) or legacy fingerprint |

All available on Linux (native + Docker) and Windows PowerShell (native providers only; Docker-deployed Windows providers use `docker exec`).

## Proxy Reload Fix

**The hot-reload mechanism had a self-reinforcing bug:** URL‑sourced proxy give-ups schedule delayed `writeReloadTrigger` calls via `time.AfterFunc`. With hundreds of failing probes each scheduling a staggered retry, triggers fired every few seconds — faster than `reload()` could complete its 3000-proxy diff. The 2-second watcher picked up each new trigger, found the file lock held, logged `reload skipped`, and retried on the next tick — forever.

Fixed with a **trailing-edge debounce** on `writeReloadTrigger`: rate-limited to one write per 30 seconds. Suppressed calls schedule a single trailing write after the debounce window closes, so late-arriving give-up retries never get silently dropped.

Also bumped the default `--proxy_url_refresh` from 15 minutes to 1 hour to reduce fetch-trigger frequency on large churny proxy lists.

## Signal Logging

When SIGTERM/SIGINT fires, the provider now logs `[signal] received %v — shutting down` before exiting. Previously the process vanished with exit 0 and no trace of what sent it. Proxy reload cycles also log `running=N desired=N lock_wait=D` on entry and duration on completion.

## Breaking Changes

- **Migration order is load-bearing**: upgrade providers **first**, then the hub, then run `urnet-tools hub onboard-cmd` and re-link. Onboarding a provider that still runs the old binary silently drops it to unverified TLS — the old code ignores `hub_ca.pem` and falls back to `InsecureSkipVerify=true`. Provider upgrade → hub upgrade → onboard, in that order.
- **New hub binary requires operator interaction on first boot.** The hub generates a fresh random password+salt on first startup — providers using the old TOFU `hub.pin` will see a fingerprint mismatch and HTTPS reporting will fail. After deploying the new hub binary, run `urnet-tools hub onboard-cmd` and re-link every provider.
- **Heartbeat staleness after re-link**: the heartbeat reporter caches its HTTP client keyed only on URL change, not trust material change. Re-linking with the same HTTPS URL leaves heartbeats failing until process restart, while reports recover immediately. The CLI's "no restart needed" is only half-true. Restart the provider if dashboard shows red dots on re-linked nodes.
- **`hub.pin` is deprecated** but still honored for one release. The new release removes the `tls.fingerprint` file that the old hub init wrote and replaces TLS cert auto-generation with the CA-based flow.
