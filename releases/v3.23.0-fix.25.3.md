# 🔐 v3.23.0-fix.25.3 — Hub CA Trust System

> **TL;DR** Password-derived CA replaces TOFU pinning. Token onboarding replaces manual `hub link` per box. Proxy reload no longer loops. Signal handler no longer silent. Provider upgrade → hub upgrade → onboard — in that order, or you'll have a bad time.

This release ships the single largest security upgrade to the hub↔provider control channel since its inception: a deterministic Certificate Authority that survives restarts, a fail-closed provider verification path that closes the old MITM window, and a zero-touch onboarding flow that you paste once and forget.

---

## 🔑 Hub CA Trust System

### 🧬 Deterministic TLS Trust

The hub derives an Ed25519 CA from an operator-chosen password using **Argon2id** (memory-hard KDF, 64 MiB, one pass at startup). Same password + same salt = same CA certificate every time. Deploy a new hub binary, lose the data dir, survive a host migration — providers trust the CA, not a one-off self-signed cert.

| 🧩 Component | 🔧 Detail |
|---|---|
| CA key | Ed25519 (deterministic, stable across Go versions) |
| Leaf cert | ECDSA P-256, 48h validity, rotated every 24h in-memory |
| KDF | Argon2id — time=3, memory=64MiB, threads=4 |
| On-disk | `hub.password` (0600), `hub.salt` (0600), `ca.crt` (0644) |

### 🛡️ Provider Verification (Fail-Closed)

> **🚨 The old behavior:** with no `hub.pin` file, the provider set `InsecureSkipVerify=true` and accepted *any* certificate. The attack window was real — between upgrading to HTTPS and running `hub link`, a MITM could intercept every report.

The new decision ladder runs at connection time and never falls through to unverified TLS:

```
📡 Non‑https URL ──────────────────→ plain HTTP (unchanged)
📜 ~/.urnetwork/hub_ca.pem exists ─→ X.509 chain verification
📌 ~/.urnetwork/hub.pin non‑empty ─→ strict pin + ⚠️ deprecation warning
💀 Nothing found ──────────────────→ hard error + remediation message
```

### 🎟️ Token-Based Onboarding

Mint a 15-minute join token once, paste the same curl one-liner into every provider. No SSH, no file copy, no `urnet-tools` on the node — just `curl | sh`.

```sh
# 🔑 On the hub (once):
urnet-tools hub onboard-cmd

# 📋 Output:
# Token:      4f3a21c9...
# Expires:    2026-07-06T15:30:00Z
# CA fingerprint: SHA256:abc123...

# 🚀 On every provider (same command):
curl -fsSL http://HUB_IP:8080/onboard.sh | sh -s -- TOKEN
```

> **💡 Pro tip:** The same token works for your whole fleet within the 15-minute window — paste once, onboard the fleet.

### 🖥️ Operator CLI

| 💎 Command | 🎯 What it does |
|---|---|
| `hub init --password "pw"` | 🔒 Set a password, enable TLS on :8443 |
| `hub init` | 🎲 Auto-generate password, enable TLS |
| `hub show-password` | 👁️ Print the password (don't paste this anywhere) |
| `hub onboard-cmd` | 🎟️ Mint a join token, print the curl one-liner |
| `hub link <url> [--token <t>]` | 🤝 Fetch CA cert (token or manual TOFU confirm) |
| `hub test <url>` | ✅ Verify TLS chain against your CA cert |

Linux (native + Docker) and Windows PowerShell — the ps1 detects Docker vs native and routes files correctly. All platforms warn before re-linking to a *different* hub host, catching accidental cross-provider contamination from shared bind mounts. Skip the prompt with `HUB_LINK_YES=1`.

## 🧩 Proxy Reload Fix

> **🐛 The bug:** URL‑sourced proxy give-ups schedule hundreds of staggered `time.AfterFunc` calls. Each fires `writeReloadTrigger`, the 2-second watcher sees a new sequence, tries `reload()`, finds the lock held from the *previous* reload, logs `skipped`, and retries on the next tick — forever. Provider bills zero bandwidth. Logs drown in skip-spam.

**🔧 The fix:** trailing-edge debounce on `writeReloadTrigger` — one write per 30 seconds, regardless of how many callers fire. Suppressed calls schedule a single delayed retry after the window closes, so late-arriving give-ups never get dropped. Also bumped `--proxy_url_refresh` from 15m → 1h.

## 📡 Signal Logging

When SIGTERM/SIGINT fires, the provider now logs `[signal] received SIGTERM — shutting down`. Previously the process vanished with exit 0 and no trace of what sent it — post-mortem diagnosis was impossible. Reload cycles also log `running=N desired=N lock_wait=D` on entry and duration on completion.

## ⚠️ Breaking Changes

> **🚨 Migration order is load-bearing.** Do not skip steps.

1. **Upgrade providers first** — old binaries with no `hub_ca.pem` silently drop to unverified TLS if you onboard them first
2. **Upgrade the hub** — generates fresh password+salt on first TLS boot, old `hub.pin` fingerprints go stale immediately
3. **Onboard** — `urnet-tools hub onboard-cmd` → paste one-liner fleet-wide
4. **Restart providers** after re-link — the heartbeat client caches by URL, not trust material, so dashboard may show 🔴 on re-linked nodes until restart

> **🔥 Legacy pin trap:** A provider still on the old `hub.pin` (leaf-fingerprint pinning) will go permanently dark once the hub upgrades. The hub's leaf cert now rotates every 24h, so the old pin can never match either the new CA-issued leaf *or* the new rotating leaf. Re-link every PIN-based provider to CA-based trust **before** upgrading the hub, or immediately after — but not at the same time without preparation. The provider-side error will say "no hub CA installed," and the fix is always `urnet-tools hub link`.

> **💔 Heartbeat gotcha:** `hub link` prints "no restart needed." For reports, this is true. For heartbeats, the client is cached keyed only on URL, not trust material. If the URL doesn't change (same-host HTTP→HTTPS upgrade), heartbeats stay broken until restart. The dashboard shows red dots on working nodes. Just restart.

> **📌 Hub.pin deprecated** — still honored for one release with a one-time warning in provider logs. Removed entirely next cycle.
