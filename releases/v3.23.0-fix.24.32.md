## What's New

### 🐛 Fix — Proxy death spiral: DNS cache, dial timeout, connecting-state leak

**Symptom**: On nodes with large proxy pools (2000+), the provider pegs 2 CPU cores at 100% with ~1800 goroutines stuck in "connecting" state during warmup. Hundreds of proxies are permanently degraded despite being alive and working on other nodes. The process thrashes swap and never recovers.

**Root Cause**: Three compounding issues:

1. **No DNS caching** (PR [#189](https://github.com/full-bars/urnetwork-3.23-fix/pull/189) regressed): The `net.DefaultResolver.LookupIP` call added in v24.31 hits the system resolver on **every** SOCKS5 dial. With 2000+ goroutines all resolving `api.bringyourapp.com` simultaneously, the resolver becomes a bottleneck, adding latency to every proxy connection attempt.

2. **No dial timeout on warmup path**: The startup warmup creates proxy goroutines with a `context.WithCancel` (no deadline). A SOCKS5 proxy that accepts TCP but never responds to the SOCKS5 handshake pins that goroutine indefinitely — no timeout in the SOCKS5 dial path to bound it.

3. **`markProxyDown` doesn't clear `connecting`**: `RegisterProxy` sets `connecting=true`, and only `markProxyUp` clears it. `markProxyDown` only sets `currentlyUp=false`, leaving the proxy stuck in "connecting" state forever if the initial attempt never succeeded. The health snapshot then reports thousands of "connecting" proxies that are actually long-abandoned.

**Fix** (PR [#190](https://github.com/full-bars/urnetwork-3.23-fix/pull/190)):

1. **DNS cache** (`net.go`): Cache hostname-to-IPv4 lookups with a 60s TTL behind `sync.Mutex`. Reduces ~2000 concurrent resolver hits to one per hostname per minute. Falls back to stale entries on transient resolver failures so a DNS blip doesn't cascade into every proxy failing.

2. **Dial timeout** (`net.go`): Apply a 30s timeout to the SOCKS5 dial **only when the caller's context has no deadline**. Paths with an existing deadline (e.g. `serialEval` with 15s `RequestTimeout`) are unaffected. The warmup path gets a safety net so a hanging proxy can't pin a goroutine forever.

3. **Connecting-state cleanup** (`proxy_health.go`): `markProxyDown` now clears `h.connecting`, matching the existing cleanup in `markProxyUp`. A proxy whose initial connection fails is properly tracked as not-connecting.

**Impact**: Warmup completes cleanly on large proxy pools. No goroutine pileup, no swap thrashing, no 100% CPU from stuck connections.
