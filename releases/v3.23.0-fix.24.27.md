## What's New

This release is a full security + reliability scrutiny pass — 12 independent fixes covering every layer of the stack, from authentication to memory management.

### 🔒 Security

- **Hub bearer token authentication** (PR [#170](https://github.com/full-bars/urnetwork-3.23-fix/pull/170)): `/api/report` and `/api/nodes/remove` now require `URNETWORK_HUB_TOKEN` via `Authorization: Bearer` header. Constant-time comparison via `crypto/subtle`. Set env var on the hub; provider-side [`bandwidth_reporter.go`](provider/bandwidth_reporter.go) sends it automatically. When unset, hub behaves as before (backward compatible). Hub report body size capped at 1MB via `http.MaxBytesReader`.

- **Cap unbounded `io.ReadAll` on HTTP responses** (PR [#180](https://github.com/full-bars/urnetwork-3.23-fix/pull/180)): Four sites where a malicious upstream server could force OOM growth are now bounded — HTTP strategy POST (8 MiB), DoH JSON/ wire queries (64 KiB each), and the internal eval-result response reader (8 MiB).

### ⚡ Stability & Correctness

- **Fix concurrent map iteration / write crash** (PR [#171](https://github.com/full-bars/urnetwork-3.23-fix/pull/171)): `RouteManager.DowngradeReceiverConnection` was iterating `transportRoutes` without the mutex. Under concurrent transport churn (`UpdateTransport`/`RemoveTransport`), this triggers Go's fatal map crash. Now properly synchronized.

- **NACK accounting leak** (PR [#172](https://github.com/full-bars/urnetwork-3.23-fix/pull/172)): `removeEventBucket` subtracted ack/syn counters on eviction but never subtracted `sendNackCount`/`sendNackByteCount` — phantom debt that permanently corrupted `ExpectedByteCountPerSecond()` for the client's lifetime.

- **SendBuffer.Ack tries all candidates** (PR [#173](https://github.com/full-bars/urnetwork-3.23-fix/pull/173)): The ack loop unconditionally `break` after the first candidate, even on sequence mismatch. With dual concurrent send sequences (client/server, companion/non-companion), this caused ~50% of acks to miss — spurious teardowns and reconnects.

- **Mode monitor never wakes waiters** (PR [#174](https://github.com/full-bars/urnetwork-3.23-fix/pull/174)): `setModeAvailable`/`setActiveMode` mutated `availableModes`/`mode` under `stateLock` but never called `NotifyAll()`. H1/H3 mode-wait loops only woke via `ctx.Done()`, so otherwise-healthy transports could be torn down unnecessarily.

- **Write-pipeline buffer leak on cancel** (PR [#175](https://github.com/full-bars/urnetwork-3.23-fix/pull/175)): Both UDP and TCP write goroutines could leak pooled `ipPacket` buffers when canceled with items still queued. Added non-blocking drain defers on both the write goroutine and the outer `Run()` function, catching items even when the main send loop re-queues them after the goroutine drain.

- **`MultiRouteSelector.Read` ignores caller context** (PR [#176](https://github.com/full-bars/urnetwork-3.23-fix/pull/176)): Was selecting on `self.ctx.Done()` instead of the passed-in `ctx`. Caller cancellation hung until the selector's own context expired.

- **Checkpoint contracts not closed on checkpoint=true** (PR [#177](https://github.com/full-bars/urnetwork-3.23-fix/pull/177)): `CloseContractWithCheckpoint` deleted tracking and bumped close count even when `checkpoint=true`. Now guarded behind `!checkpoint`.

- **Client replace cleanup bypassed** (PR [#178](https://github.com/full-bars/urnetwork-3.23-fix/pull/178)): `multiClientWindow.expand()` used bare `Cancel()` on the replaced client instead of `clientRemoveCallback`, leaking `clientUpdates` map entries and leaving in-flight flows uncleaned.

- **Data channel not closed on peer connection teardown** (PR [#179](https://github.com/full-bars/urnetwork-3.23-fix/pull/179)): `peerConn.Run()`'s deferred cleanup only closed `self.pc` (the WebRTC peer connection). The detached data channel (`self.conn`) is now closed alongside it.

- **JWT write error silently ignored** (PR [#181](https://github.com/full-bars/urnetwork-3.23-fix/pull/181)): `os.WriteFile(jwtPath, ...)` error was unchecked. Disk-full or permission failures were masked until the next restart hit the single-use-auth-code fatal path. Now fatally logged.
