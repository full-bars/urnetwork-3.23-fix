# v3.23.0-fix.34.2

> [!NOTE]
> This is a patch on v3.23.0-fix.34.1. The provider now reports an upstream-style version to the backend, and the Linux installer picks up its distro fixes and a four-distro test. There is nothing to configure and no operator action beyond the normal update and restart. Provider traffic behavior is unchanged.

> [!IMPORTANT]
> This release tags as `v3.23.0-fix.34.2`, but the provider reports a different string to the backend: `YYYY.M.D-<code>-fix.34.2`. Both belong to the same build. The git tag is what `urnet-tools update`, the installers and Docker use. The calendar string is what the platform sees in the connect auth. The two are never mixed, so nothing you run today changes.

## Which version is reported where

| Where | Value for this release | Notes |
|-------|------------------------|-------|
| Git tag, GitHub release, Docker tag, `urnet-tools update` | `v3.23.0-fix.34.2` | Unchanged. |
| Provider log lines, metrics, `provider --version`, hotswap, dashboard label | `v3.23.0-fix.34.2` | Unchanged. |
| The `[health][build]` heartbeat line | both | New `reports=` field, see below. |
| Connect auth `app_version` and the `X-UR-AppVersion` header (what the platform records) | `2026.M.D-<code>-fix.34.2` | New. Example for 34.1's commit: `2026.10.20-1076955500-fix.34.1`. |

The reported string has three parts:

1. **Date** (`2026.10.20`): the UTC commit date of the tagged commit, written `YYYY.M.D` with no zero padding. This is the part the platform's provider rollout gauge keeps. It drops everything from the first `-` onward, and groups a version that does not start with a real date, including every earlier 3.23 tag, under `other`.
2. **Build code** (`1076955500`): the URnetwork house build code, `(seconds since 2023-05-23T00:00:00Z) x 10` taken at the tagged commit's time. It is the same formula upstream's tooling uses for its `v2026.10.20-1077000950` style tags and the meso-miner tags, so it decodes back to a mint time. The platform stores it with the full string in `device.client_version` (64 characters at most) and does not read it.
3. **Fork marker** (`fix.34.2`): the fix release number, so a node reported to the platform stays identifiable as this line and release.

A release candidate tag keeps its suffix, so `v3.23.0-fix.34.2-rc1` reports `...-fix.34.2-rc1`.

The `[health][build]` line that leads every heartbeat tick shows both, so one log line ties the build to what the platform records:

```
[health][build] v3.23.0-fix.34.2 profile=auto host=node-a reports=2026.10.21-1077100000-fix.34.2
```

The first field is the git tag. `reports=` appears only when the two differ, so a build without the flag looks exactly as before.

Compute the exact string for any release tag with `scripts/compute-app-version.sh <tag>`. The tag's build log prints the value the release was built with. The 34.2 value is filled in below once its commit is tagged.

**34.2 reports:** `TO BE FILLED IN AT TAG TIME`

> [!NOTE]
> The platform's modern provider gate does not read this string. It measures post-quantum end-to-end encryption and resizable transfer windows directly, and both have been in the provider since v3.23.0-fix.33. Reporting an upstream-style version changes how a node is recorded and counted by release. It does not change how a node is classed as modern.

## What's Changed

### Added

- **The provider reports an upstream-style version to the backend** (`provider/main.go`, `provider/client_limit_hold.go`, `scripts/compute-app-version.sh`): the connect auth carried the raw git tag, which the platform's version parser reads as year 3 and files under `other`, and it stored a value no tool could group by release. `AuthVersion` (set with `-X main.AuthVersion=...`) is now the auth's `app_version`. `RequireVersion()` is unchanged, so logs, metrics, hotswap, the dashboard label and the update checks keep the tag. A build without the flag reports its plain version as before. The Docker image (`APP_VERSION` build arg), `build.yml` and the provider step of `release.yml` pass the flag on tag builds only. `urnet-tools` and `urnet-docker` never authenticate, so they are unchanged. The shakedown and installer-matrix jobs, main-branch Docker builds and a plain `make` build keep reporting the plain version.

### Fixed

- **The installer installs missing download and JSON dependencies** (`scripts/Provider_Install_Linux.sh`): a minimal host has neither curl nor a JSON parser, so a first-run install stopped with a package-manager instruction. It now installs only what is missing through the host's own package manager (apt, dnf, yum, zypper, pacman, apk). `URNET_NO_AUTOINSTALL=1` keeps the old refusal.
- **`URNET_NO_AUTOINSTALL` is honored by both dependency paths**: a second dependency path had been added beside the existing one, so the opt-out never applied. The existing helpers are kept, the downloader is sudo-aware, and both stop when the opt-out is set.
- **The installer uses `yum` when `dnf` is absent**: Amazon Linux 2 reports `ID=amzn` and ships only yum, so the helpers failed there with `dnf: command not found` before the installer could run.
- **The root prompt stays off a non-interactive run**: under Docker the tty node exists but cannot be opened, so the root-with-systemd prompt read an empty choice and exited 1. The guard now probes by opening `/dev/tty`, and `-f` takes the documented tools-only path instead of prompting.

### Changed

- **The installer runs on four distros in CI** (`.github/workflows/installer-matrix.yml`): Debian 12 and 13, the RHEL family and Alpine, against a local fake release. It asserts the install tree, version, reinstall, tag switch and uninstall.
- **Release publication waits for the installer tier** (`.github/workflows/release.yml`): a red installer matrix never blocked a release, because it is a separate workflow on the same tag. Publication now waits for the matrix run on the commit and fails when an installer cell failed. It reports only until two clean tag runs, then blocks.
- **Examples and comments use placeholder hosts**: log excerpts, design examples, comments and one fixture named real hosts and a real home directory. They now use TEST-NET addresses and generic descriptions.

## Deploy Notes

1. **Update and restart.** `urnet-tools update` picks up the release. No config change, no new setting and no migration.
2. **Check one node first.** After the update, the platform records the new string for that node. If you can read `device.client_version` or the provider rollout gauge, confirm the node shows the calendar form. The provider's own logs still print `v3.23.0-fix.34.2`.
3. **Docker.** The image passes `APP_VERSION` at build time, so the container reports the calendar form. An image built locally without the build arg reports the plain tag.
4. **Rollback is the usual patch rollback.** Keep the previous provider binary and a state tarball, stop the unit, restore the binary, start.
5. **Docs.** [Node Identity](../docs/Node-Identity.md) explains the dashboard label against the reported version.
